# Package 130: the game on a machine without Python (Windows and Mac)

*The builder's design and report. The brief: `docs/dev/briefs/Brief-Package130.md`. The owner's word of 2026-11-27: "let's build it for Windows and Mac. I won't be able to test the Mac version myself, but that is alright."*

## What was wanted, and what there is

A player who has never heard of Python downloads one file, unpacks it, opens one thing, and the harbour is in their browser. There are now two downloads, built from any commit by the repository's own workflow:

- **`FreeSail-NAME-windows.zip`** (about 450 MB): Windows 10 and 11, 64-bit.
- **`FreeSail-NAME-mac.zip`** (about 515 MB): macOS 12 and later, Apple silicon and Intel in the one download.

Each unpacks, by its system's own unpacking, to one folder holding, at its top, **one thing to open** (`FreeSail.cmd`, which Windows shows as "FreeSail", a Windows Command Script; `FreeSail.command` on the Mac, which Terminal runs on a double-click), the **"start here" page** (`START HERE.txt`), and beside them the game (`game/`), its own Python (`python/`; on the Mac `python-arm64/` and `python-x86_64/`) and the licences (`licences/`). Nothing of the game changed: the launcher runs `python -m freesail` with the folder's own interpreter, which opens the harbour as it always has.

The pieces in the repository:

| piece | what it is |
|---|---|
| `tools/bundle.py` | assembles each download from a checkout (`windows`, `mac`), lists the game's files it ships (`files`), and resolves the lock files again (`lock`) |
| `tools/bundle/` | the launchers, the two "start here" pages, the three lock files, and python-build-standalone's licence texts |
| `tools/bundle_smoke.py` | the smoke test of a built zip, on the system it is for |
| `.github/workflows/downloads.yml` | builds both, smoke-tests them on Windows and both Macs, and publishes a pre-release when asked |
| `.github/workflows/release.yml` | the gate's release, which now calls the above and attaches both downloads beside the project's zip |
| `tests/test_downloads.py` | truths 7-800 to 7-809, in the ordinary suite; a change to it runs the downloads workflow again |

## What the game opens, and so what ships

Measured with Python's audit hook on every file opened (the `open` event), in process: the server's app as `py -m freesail` makes it, the harbour's page, state and catalogue, *A first passage* begun from the catalogue's first game, the game's page, state and ship, sixty ticks, the primer's chapter 7 and the library's topics, the harbour's chart, a save, and a second game on the Channel's chart (*The tender*) with its minute and its chart (the first passage is in open water and opens none of the depth tiles; the tender opens them).

|---|---|---|

| `data/` | about 660 (every scenario, ship, port, evolution and signal book the catalogue and a game read; the coast, features and overrides of the charts; nine depth tiles for the tender) | 15 MB |

Read as well, by the code's own paths: `docs/agents/ConsentBrief.md` when a model is seated, and `docs/agents/consent/` (the records). Nothing is written under the repository in that run; the save and its checkpoint go to the saves place.

So what ships is **a rule, not a list** (`bundle.game_files`): every file git tracks under `freesail/`, `client/`, `data/` and `docs/primer/`, and `README.md` and `docs/agents/ConsentBrief.md`. That is 3,309 files and 420.3 MB (decimal megabytes; 400.9 MiB) at this commit, of which the charts' tiles are 397.5 MB: a game in another region opens other tiles, so all of them ship. **Not shipped**: the owner's consent records (`docs/agents/consent/`, which carry the names of the models they have seated: a friend's model is asked its own consent), the tests, the tools and the rest of the documents. Truth 7-800 repeats the measurement on every push and fails if any file the game opened lies outside the rule, whatever `data/` holds; a ship, scenario or chart added to `data/` is inside the rule without anyone remembering it.

## The Windows road

- **The interpreter**: python.org's embeddable package, CPython **3.11.9** for amd64 (`python-3.11.9-embed-amd64.zip`, sha256 `009d6bf7e3b2ddca3d784fa09f90fe54336d5b60f0e0f305c37f400bf83cfd3b`). 3.11.9 is the last 3.11 python.org built for Windows; the line has been source-only since. It is the version the game is developed on (3.11), and the embeddable package is made to be carried inside another program's folder.
- **Nothing outside the folder is read.** The interpreter's `python311._pth` is rewritten to name the only places it imports from: `python311.zip`, its own folder, `Lib\site-packages` and `..\game`, and `import site` (so that the libraries' `.pth` files run: pywin32's, which the agents' extra brings on Windows, needs it). The presence of a `._pth` file makes Python ignore `PYTHONPATH`, `PYTHONHOME` and the registry; the launcher also passes `-I` (the interpreter reads no user site-packages, no `PYTHON*` variable, and puts neither the script's folder nor the one it is started from on its path), `-B` (no `__pycache__` written beside the code) and `-X utf8`, and runs `python\python.exe` by its absolute path, never by the PATH. For anything the game starts (a door at a station) it clears four named variables, `PYTHONHOME`, `PYTHONPATH`, `PYTHONSTARTUP` and `PYTHONUSERBASE` (the Mac's launcher clears six: those four, `PYTHONEXECUTABLE` and `__PYVENV_LAUNCHER__`), and sets `PYTHONDONTWRITEBYTECODE`, `PYTHONNOUSERSITE` and `PYTHONUTF8`; no other variable is cleared, and it is `-I` and the `._pth`, not the clearing, that keep the rest out (the smoke test's poison, below, is placed where no clearing reaches).
- **The dependencies** are installed at the build, on Linux, for Windows: `pip install --target python\Lib\site-packages --platform win_amd64 --python-version 3.11 --implementation cp --only-binary=:all: --no-deps --require-hashes --no-compile -r tools/bundle/locks/windows-x86_64.txt`. Wheels only, each checked against the lock's sha256, no dependency resolved at the build, nothing compiled; pip's console scripts (which name the build machine's Python) are removed.
- **No precompiled bytecode** is shipped: compiling the game and its libraries in memory at each start costs about 1.5 s (measured), and shipping bytecode would double the file count of a zip a player unpacks with Explorer. `-B` keeps the folder unwritten.
- **The launcher, `FreeSail.cmd`**, titles its window "FreeSail", says in plain words that this window is the game's server and to keep it open, that the browser opens the harbour at `http://localhost:8000/harbour`, to begin with *A first passage*, how to stop (close the window, or Ctrl+C and Y to cmd's "Terminate batch job (Y/N)?"), and that the saves and settings are in `%APPDATA%\FreeSail` and survive a newer download. When the game stops it says so with its exit code, and waits for a key. Opened from inside the zip without unpacking (Explorer lets a zip be opened like a folder), it says to "Extract All" first, and names the folder that makes, instead of failing in Python's words.
- **One folder, not a folder in a folder.** "Extract All" makes a folder of the zip's own name and lays the zip's entries in it, so a zip holding a folder unpacks to `FreeSail-NAME-windows\FreeSail-NAME-windows\`, and a stranger who opens the first sees only another folder (the reader's finding). So the Windows zip holds no folder: its entries (`FreeSail.cmd`, `START HERE.txt`, `game\`, `python\`, `licences\`, `LICENCES.txt`) lie at its top, and "Extract All" makes the one folder `FreeSail-NAME-windows` with the launcher at its top; the page and the launcher's "not unpacked" words name that folder. (The Mac's zip keeps its one folder: Archive Utility makes the folder a zip holds, and no other.) The smoke test unpacks as "Extract All" does, into a folder named for the zip, and checks that the unpacking makes one folder with the launcher at its top, on both systems. Another tool's "Extract Here" (7-Zip's) would spill the loose files where the zip lies: the page has a line for it, to unpack into a new folder of its own (held by truth 7-804). It passes its arguments on (`FreeSail.cmd --no-browser --port N`, used by the smoke test).
- **What Windows says the first time.** Files unpacked by Explorer from a downloaded zip carry the "mark of the web", and a script with it from no known publisher meets one of two warnings, which the "start here" page names both of: Microsoft Defender SmartScreen's "Windows protected your PC" (*More info*, then *Run anyway*), or the older "Open File - Security Warning ... The publisher could not be verified. Are you sure you want to run this software?" (*Run*). **This part is from Microsoft's documented behaviour, not measured**: a cloud runner has no desktop to show a dialog in, and Expand-Archive does not pass the mark on. One risk is named and not built for: on a Windows 11 machine where **Smart App Control** is switched on (new installations, in its evaluation mode), unsigned DLLs (the libraries' `.pyd` files) can be refused; signing (below) is what removes it, and switching Smart App Control off is the player's only other road.

## The Mac road, and the two not taken

**Chosen: a relocatable Python carried in the download, the launcher clearing the quarantine on its own folder.**

- **The interpreters**: python.org builds no relocatable Python for macOS (only its `.pkg` installer, which installs into `/Library/Frameworks`), so they are python-build-standalone's CPython **3.11.15** (release 20260718), `aarch64-apple-darwin` and `x86_64-apple-darwin`, `install_only_stripped`, from the project's own GitHub releases (sha256 `b21dbc3f3e01932fcc3f0f4c51e5a7ef61888cb454d23eee6e8207c6f52d0b04` and `8ca3906ed23f4a8ab4ff8f02d61b15ecf62e6fa8b312cd59d1692df34e834a65`, as that release's SHA256SUMS gives them). They are the builds uv installs, made to be moved. Both go in the one download, about 40 MB each with their libraries, so that a friend need not know which Mac they have; the launcher picks by `uname -m`. The game is put on each interpreter's path by a one-line `.pth` file in its site-packages (`../../../../game`), which `-I` leaves working (it turns off the user's site, not the interpreter's own).
- **What the interpreter brought and the game never runs is taken out** (`bundle.strip_interpreter`, the reader's finding): python-build-standalone's build carries its own pip 26.1.2 and setuptools 82.0.1 in its site-packages (with `_distutils_hack` and `distutils-precedence.pth`), pip's console scripts in `bin/`, ensurepip's wheels of both, and four compiled `.pyc` files (three of `encodings`, one of `_distutils_hack`). Before the lock file's libraries go in, all of it is removed, and the build refuses to go on if the site-packages then holds anything but its README. So `LICENCES.txt` lists the lock file's libraries alone, truly, and nothing unneeded ships; the smoke tests on both Macs are the proof that the interpreter starts and the game runs without them. (Windows' embeddable package carries no pip.)
- **The libraries** come in as on Windows, for `macosx_12_0_arm64` and `macosx_12_0_x86_64` (pip accepts the older macOS tags under them; the arm64 wheels say 11.0), from a lock file per architecture. The Intel lock differs in one place: cryptography's wheels for Intel Macs stop at 48.0.1, so the lock is resolved wheels-only for each platform (`uv pip compile --only-binary :all: --python-platform ...`) and takes 48.0.1 there.
- **Gatekeeper.** A browser marks what it downloads with the `com.apple.quarantine` attribute, and the Mac's unpacker (Archive Utility, and Safari's own unzipping) passes the mark to every file it unpacks. A marked program from no identified developer is refused when it is first opened: on macOS 12 to 14 "“FreeSail.command” cannot be opened because it is from an unidentified developer" (or "... the developer cannot be verified"), passed by Control-click, *Open*, and *Open* in the box "macOS cannot verify the developer of “FreeSail.command”. Are you sure you want to open it?"; on macOS 15 and later "“FreeSail.command” Not Opened" ("Apple could not verify ... is free of malware"), passed by *Done*, then System Settings, Privacy & Security, *Open Anyway*, the password, and *Open Anyway* again. That is the one step, and it is the player's own decision. If nothing else were done, every marked executable and library the interpreter then loaded (the interpreter, and hundreds of `.so` files) would each meet Gatekeeper in turn. So the launcher's first act, once the player has let it run, is `xattr -dr com.apple.quarantine` on the download's own four folders, named one by one (`python-arm64`, `python-x86_64`, `game`, `licences`): the files are theirs, it needs no password, and it touches nothing else, not even the folder they lie in. Truth 7-804 holds the launcher to those four operands and no other. The smoke test gives the zip the mark a browser gives, unpacks it with `ditto` (which passes the mark on as Archive Utility does), checks the files carry it, checks the launcher cleared it in the four folders, and checks that what must keep its mark keeps it: the folder itself, `FreeSail.command`, `LICENCES.txt` and `START HERE.txt`, exactly.
- **The other prompt** a friend may meet: Terminal asking once whether it may access files in their Downloads (or Desktop, or Documents) folder, macOS's privacy rule for those folders. The page says to click OK.
- **Not taken, (b): the interpreter fetched at first start** by the launcher (curl, then the sha256 checked). curl's downloads carry no quarantine mark, so the clearing would not be needed, but the launcher itself is refused once all the same (it came by a browser), so the player's steps are no fewer; and it needs the network at the first start, and the one place the interpreter comes from to be up that evening. It saves 80 MB of download and costs a second way to fail.
- **Not taken, (c): the player's own Python 3.11 or later**, with a clear word if they have none. Most Macs have none (the `python3` Apple ships is a stub that offers to install the developer tools, and is 3.9). Installing python.org's is a second program to install, and the game's libraries would then need pip and the network: two obstacles, which the brief rules out.
- **A Linux download does not fall out for nothing**: it would want another interpreter, another lock file, and another runner in the smoke test. None is built; the README's two lines serve.

## The workflows

`.github/workflows/downloads.yml` runs in three ways. **By hand**, "Run workflow" on any branch with a name typed: builds, smoke-tests, and publishes the pre-release `preview-NAME` (an earlier one of that name replaced), for handing to friends between gates. (GitHub offers "Run workflow" only for a workflow on the default branch, so this appears once the file is on the trunk.) **Called by the gate's release**, which attaches both downloads beside the project's zip once their smoke tests have passed. **On a push that changes the downloads' own files** (`tools/bundle.py`, `tools/bundle/**`, `tools/bundle_smoke.py`, the workflow): builds and smoke-tests, so that the macOS runners run when a download has changed and not on every push (and when `pyproject.toml` or the truths of what ships, `tests/test_downloads.py`, change). **A push publishes nothing**: a release is made by the owner's hand or by a gate, never by the words of a commit. While the package was built, a line of its own in a pushed commit's message published a draft, to prove the publishing without a public release; that was proven at `d762257` by run 46087525336 (the draft `preview-pkg-130`), and the door was then closed at the lead's word (2026-11-28).

The build job's Python is setup-python's CPython 3.11.14 exactly (the harness's too): it runs pip and writes the zip, so it is pinned to a patch release rather than "3.11"; its download is setup-python's own (not checksummed by us), and every byte it puts in a zip is checked against a pin. ## Signing and notarising: what each would cost, and remove

Nothing is built for either. **Windows**: an Authenticode code-signing certificate from a public authority costs roughly US$200 to $500 a year (since 2023 its key must live on a hardware token or a cloud signing service, which a workflow can use); Microsoft's own cloud signing service is cheaper (about $10 a month) where its eligibility rules admit an individual. A signed launcher and signed libraries replace "unknown publisher" by the owner's name, and satisfy Smart App Control; SmartScreen's "Windows protected your PC" still appears for a new publisher until enough downloads have built a reputation (an EV certificate no longer skips that). The launcher would need to become a small signed `.exe`, as a `.cmd` file cannot carry a signature. **Mac**: the Apple Developer Program costs US$99 a year; with a Developer ID certificate every executable and library in the download is signed and the zip notarised by Apple, and Gatekeeper then opens the download with only its ordinary "downloaded from the internet, are you sure?" box, with no Control-click, no System Settings and no clearing of the quarantine. It wants the launcher made into an `.app` (a `.command` cannot be notarised as an app) and a Mac in the workflow, which the cloud's runners are. Both are the owner's money and decisions; the figures are as of this writing and theirs to check.
