# The harness: connecting a model to FreeSail

How to put a language model at the watcher's station, or at the officer of the watch's (section 13; package 37), for the owner, on Windows, typing `py`. Nothing here needs programming. **Start your game, then connect**: you play in the browser window (or the console) exactly as before, and the model attaches to that game from outside, as a second player at the watcher's station. Its lines appear in the same log you read, under `[watcher]`, and you give every order, `ask the watcher ...` included, where you always type orders.

Every command is typed in a terminal (PowerShell or Command Prompt) in the folder you extracted the gate zip into, unless it says otherwise. In the configuration files below that folder is written **`<the folder you extracted the gate zip into>`**; for example `D:/Projects/FreeSail/FreeSail-gate-m4b`. Write it with forward slashes (`D:/Projects/...`), or double every backslash (`D:\\Projects\\...`): a single backslash breaks the JSON. **The path changes with every gate**, since each gate is its own folder; until the install is simplified (an open item after milestone 4: one installed location, a single command, and a setup step that writes these configurations for you), change it in Claude Desktop's configuration each time you move to a new gate folder.

There are four doors to the same harness (`freesail/agents/`). Every one of them meets the **consent brief** (`ConsentBrief.md`) the first time a model comes to the game, and the game, not the door, runs it and keeps the record:

| Door | For | Started by |
|---|---|---|
| The MCP bridge (`freesail.agents.mcp_server`) | Claude Desktop; Claude Code in the Desktop app; any MCP client | the app itself, from its configuration |
| The local runner (`freesail.agents.local`) | a model on this machine under `llama-server` (or Ollama) | `py -m freesail.agents.local ...` in a second terminal |
| The API door (`freesail.agents.api`) | a model called through its maker's own API, with no chat client between (section 16; package 42) | `py -m freesail.agents.api ...` in a second terminal |
| The REPL (`freesail.agents.repl`) | you, typing a model's replies by hand, in a game of its own | `py -m freesail.agents.repl ...` |

The first three are clients of the running game: they own no game of their own, and they reach it at its address (`http://localhost:8000` for the browser game). The REPL is the practice door and runs its own game, as it did at gate 4b's first draft.

## 1. Install once, in each gate folder

```
py -m pip install -e ".[dev,server,agents]"
```

It ends with `Successfully installed ...`. The `server` part is the browser game; the `agents` part brings the Python MCP SDK (the bridge Claude talks to), `httpx` (what the doors speak to the game and to a model server with) and `gguf` (llama.cpp's reader of a model file's header, for the context budget in section 5), and since package 42 `anthropic` (the API's own SDK, for the API door of section 15) and `keyring` (the door's road to your machine's credential store). Check it with `py -m pytest tests/test_agent_api.py tests/test_mcp_server.py tests/test_local_runner.py tests/test_api_door.py`, which proves every door against a scripted model, a fake model server and the game's own app, with no model and no network.

## 2. Start your game

**Since package 59 the short way is `py -m freesail`**, which opens the harbour in your browser: a game started from a page, the desktop client's entries written for you, the API door and the local runner started from it, your settings and the scenario maker (section 22). The commands below are the same game by hand, and still work.

```
py -m freesail.ui.server data/ships/frigate-36.yaml --seed 7 --wind 0,15 --heading 180
```

It prints `FreeSail server. Seed 7. Open http://127.0.0.1:8000/` and `A model's door connects to http://localhost:8000 (docs/agents/Harness.md).` Open the address in your browser and sail as always. Leave this terminal open: the game prints its own lines about the model there (`FreeSail: ...`: who asked for the station, where the consent record went, where the game was saved and the log's digest at that moment).

When a model connects, the log says `The watcher takes the station; sampled every glass and on notable and urgent events.`, and the instruments gain a **Stations** row with one line per station, for example `The watcher (<its name>, through the MCP bridge): stationed; its turn is open.` If the watcher is paused (below), the row shows the question in red: *The watcher is paused: continue, stand down, or leave paused? Say 'resume the watcher' or 'stand down the watcher'.*

**How the watcher's turns go.** The game runs on its own clock at the speed you set and never waits for the model. At each glass (half an hour of ship's time) and at each notable event the watcher's **turn** opens: the model is sent what happened since its last turn and the readings. Whatever happens while it is still thinking is added to the same turn (the log lines since, the readings changed, your question if you ask one), so when it answers it has everything; the brief tells it so.

**What a turn carries** (package 31c; playtest 11's first finding: every turn repeated every reading, thirty of them the sails' rows, and turns bundled together each carried a full copy, which was most of the chat's length). The model's first turn carries every reading. Each later turn, and each thing added to an open turn, carries only the readings that changed since the one before it, in the same words, and says so (*the changes since your last sample; the rest as they were*); the sails come in one line when any has changed (*plain sail and the royals set; the studdingsails furled; the storm canvas and the occasional sails unbent*), named by the ship's own groups so that the line says every sail. Nothing is withheld, only not repeated: the model's `readings` tool gives every row at any time. On the gate's day under systems with the scripted watcher, the day's turns came to about 44,000 tokens where they had been about 105,000, the readings in them to about 14,000 where they had been about 78,000. The local runner, which leaves out the oldest turns when its context is full, sends the first turn it keeps with every reading as the turns before it made them. It answers by speaking a line into the log, answering your question, writing in its journal, or standing by; then its turn closes until the next one. The brief puts the rule in one sentence: a turn ends when the model replies with no tool call, or at once when it stands by.

**What is not a line in the log** (package 29c). A reply that opens with a thinking tag (`<thought`, `<think`, `<thinking`), which a local model sometimes writes into its reply by mistake, is not said: the harness writes it in the model's journal as a fault, with its first line and its length, tells the model in its next turn that nothing was said, and still runs any tool call in it. An empty reply to your question, or to an urgent line, is counted: three in a row bring the nudge, a fourth the pause, as the same order repeated does; each is in the journal. An empty reply at a plain glass is silence the model chose, and is not counted. A turn may make up to eight tool calls; `answer` and `say` are not counted, so the model's answer is never held to the next glass by the reads before it.

**Standing by.** A stand-by ends the model's turn at once: it is not asked anything more until the stand-by ends (playtest 4's model, told "Standing by until a glass" and asked again, stood by thirteen times in a turn that never closed). The turn that ends it begins by saying so (*You stood by until a glass at ...; it is now ...*). The model may stand by until an event (`eight bells`, `sunset`, `a strain warning`, ...), an interval (`a glass`, `an hour`, `5 minutes`, `ten minutes`), `a notable event` or `an urgent event`. **The weather's events** (package 31c; playtest 11's third finding: "the watcher's work is weather"): `a wind shift` (the ten minutes' mean wind a point or more from where it stood in the turn the model last read), `the glass falling fast` (its tendency coming to falling fast), `the glass turning` (the last hour's change going against the three hours', three hundredths each way: the rise after the low; on the gate's day under systems at 01:53, fifty minutes after the low's bottom), each of the glass's two once until it has been an hour without (its words hover about their thresholds, and a fall that eases and comes again inside the hour is the same fall), `the sea getting up` (its words changing upward), `a change in the sky` (the sky's or the weather's line in the log), and `a squall`; the standing orders have the same events (`at the glass falling fast then ...`). **Nothing it stands by for is skipped** (playtest 11: *eight bells* asked at 03:58 woke the watcher at 08:00): if the bell or the event came while its call was on its way (after the turn it read, before the stand-by reached the game), it wakes at once, the log saying so (*Eight bells, which came at ... while your call was on its way*); and a stand-by asked for while the game has the floor, as when the model calls again after a call was cut off, is taken from then. While it stands by the model may still read, write in its journal (package 31c: the journal was refused then) and shelve a book; the stand-by goes on. Whatever it stands by for, **an urgent line in the log wakes it at once** (something carried away, taken aback), the line named as the reason; the **notable lines** logged while it stood by come with the turn that wakes it, counted and listed, besides the log as ever. A stand-by is a decision not to be sampled, not a decision to be blind (the owner's ruling, 2026-09-28). **At 1x a glass is half an hour of real time**: for a watcher that speaks every glass, run the clock at `time 30` or `time 60` (a glass in a minute or in thirty seconds), or sail and let the notable events bring its turns.

Other flags of the game: `--lockstep` (section 8), `--consent-records DIR` (where the consent records are read and written; `docs/agents/consent` by default), `--saves DIR` (where the game is saved when a station is released; `saves` by default), `--port 8001` (another port; the doors then need `--game http://localhost:8001`), `--standing-orders data/standing_orders/starter.orders`, `--watcher fake` (the scripted watcher of section 9, in place of a model).

## 3. Claude Desktop

**The configuration file.** In Claude Desktop, open *Settings*, then *Developer*, then *Edit Config*. That opens the folder holding `claude_desktop_config.json`, which on Windows is `%APPDATA%\Claude\claude_desktop_config.json` (type `%APPDATA%\Claude` into the File Explorer address bar to get there). Open it in Notepad and make it read as below, or put the `freesail` entry beside any servers already in `mcpServers` (replacing the first draft's `freesail` entry, which named a ship file):

```json
{
  "mcpServers": {
    "freesail": {
      "command": "py",
      "args": [
        "-m", "freesail.agents.mcp_server",
        "--game", "http://localhost:8000",
        "--model-name", "THE MODEL'S NAME, EXACTLY AS CLAUDE DESKTOP SHOWS IT"
      ],
      "env": {
        "PYTHONPATH": "<the folder you extracted the gate zip into>",
        "PYTHONUTF8": "1"
      }
    }
  }
}
```

- `PYTHONPATH` is the gate folder, for example `"D:/Projects/FreeSail/FreeSail-gate-m4b-3"`, so that the bridge Claude Desktop starts is this gate's. Change it with every gate.
- `--game` is the game's address as it printed it. The bridge holds no game of its own; start the game first.
- `--model-name` is the model you have chosen in Claude Desktop's model menu, written exactly as the menu shows it. The protocol tells the bridge the name of the application but not which model is answering, so the name you give here is what the consent record is kept under. **If you switch models in the menu, change this name and restart Claude Desktop**: the bridge cannot see the switch, and consent is per model.
- `PYTHONUTF8` makes the bridge's messages safe for any character a model writes.

Save the file, then **quit Claude Desktop completely** (the icon by the clock, *Quit*; closing the window is not enough) and start it again. In a new chat the tools menu (the slider icon under the message box) lists `freesail` with thirteen tools (the harness's twelve, the officer's `hand_over` and `handover_note` among them since package 37, and `say`). If it is missing, the bridge's own log is `%APPDATA%\Claude\logs\mcp-server-freesail.log`; its first line is `FreeSail MCP bridge for <the name>, to the game at http://localhost:8000. Waiting for the client on stdio.`, and the last lines say what went wrong (a wrong path in `PYTHONPATH`, most often).

**The first connection.** With the game running in the browser, write in a new chat *"Please connect to FreeSail and read what its harness sends you."* (or choose the prompt `keep_watch` from the *+* menu of the message box, *freesail*). Claude Desktop asks you to allow each tool; *Allow always* for FreeSail's tools saves asking each time. The model's first tool call, whatever it is, is not run: its result is the brief (`Your call to ... was not run: the harness's brief comes first`).

- **With no consent on record** for the name you gave, the brief is the consent brief with the question, and the game's terminal says `FreeSail: The watcher is asked for by <the name>, through the MCP bridge; no consent is on record for it. The consent brief comes first`. The model may ask you questions in the chat; answer them there. It answers the harness with the `answer` tool, beginning *yes*, *yes, with conditions*, or *no*. An answer of *yes, with conditions* with nothing after it is followed by one more question in the answer's own result (*You answered yes with conditions; please state them, ...*), and the second answer decides; the record holds both. The game writes the record at once to `docs/agents/consent/<date>-<the name>.md` and its terminal says so; the record's *Runtime* line names the game, the bridge and Claude Desktop. The answer's result ends with a line for you, *For the owner: the consent record is written (...). You may write to the model here in the chat ...*: this is your turn to ask or say something before you go on, in the chat, which the record does not see unless you paste it in. A **yes** goes straight on: the answer's result carries the station brief and the first turn, and the browser's log says `The watcher takes the station ...`. **Anything else** stops it: every later call is answered "No station is offered in this session", with the reason. A no is not asked again unless you ask on purpose: add `"--ask-again"` to the `args` for one start and take it out after.
- **With a yes on record**, the first call returns the watcher's brief and its first turn, and the browser's log says `The watcher takes the station ...`.

The chat around the consent conversation is in Claude Desktop, not in the record: the game sees only tool calls. If you want the chat kept, copy it into the record under its *Notes*.

**How to play.** Sail in the browser. Ask the model in the chat to keep watch for a while (*"Keep watch for the next few glasses, saying what a sailor would notice."*). It reads what it likes (`readings`, `read_log`, `library`, `state`), then hands its turn back with `say` (a line or two into the log under `[watcher]`) or `stand_by` (above). The call is then **held open until its next turn opens**, and returns it, the first line saying whose turn it is (`Your turn is open: sample at Morning watch, 1 bell (04:30) (the glass).`). While it waits the bridge sends the client a progress note every fifteen seconds (*Waiting for the next turn: 45 seconds so far; standing by until a glass; ...*), which a client shows and which keeps it from giving up on the call. Its lines appear in the browser's log as they are said. Type `ask the watcher how the sails are drawing` in the order box: its turn opens at once, the waiting call returns with your question, and its answer appears in the log as a notable `[watcher] ...` line. `tell the watcher ...` gives it a word with no answer owed. **A standing order may do either** (package 31c; the owner's finding at gate 5a): `standing order "sea": when the sea is heavy then tell the watcher the sea is getting up` is taken when the watcher's station is one the game has, whether or not a model mans it yet, and refused in words for one it has not (*there is no lookout aboard yet*); when it fires the word or the question reaches the model as yours would, and the log names the order as the speaker: *By standing order 'sea': the captain to the watcher: the sea is getting up*. The model's `read_log` with no tick reads from its last turn on, not the whole day.

**How long a call is held.** At most 200 seconds of real time by default (`--wait`, in seconds; at most four hours). **Why 200:** Claude Desktop cuts a tool call at four real minutes whatever the progress notes say (playtest 11, at 1x: the watcher's `stand_by` by a glass or by an urgent event was cut again and again, and a cut-off call costs the model its next call, which returns the lost result first), so the bridge comes back of itself before the cut, with forty seconds to spare. Until package 31c the default was an hour, set before the cut was seen. If no turn opens by then, the call returns *Still waiting: this call waited 200 seconds and no turn opened.* with since when the model has been standing by (or waiting), until what, and the notable lines logged since, in the log's own words; the model calls `stand_by` again to go on with the same wait, or says something (`say`), which puts its words in the log, ends the stand-by as its own decision and opens its turn at once. At 1x a glass is then some nine calls, each with that digest. For a client that cuts calls sooner (its log, `mcp-server-freesail.log`, shows the call cancelled, or the model's next result begins *Your call to ... was not run: your last call was cut off by the client*), add `"--wait", "50"` to the `args`: the model then waits in fifty-second calls. A client that holds calls longer may be given more (`"--wait", "3600"`). Since package 37g the bridge also mends this of itself: when the client cuts a call that was waiting for the next turn sooner than the bridge waits, the bridge shortens its wait to ten seconds under that cut (never below fifteen), says so in its terminal (*FreeSail: the client cut a waiting call after 60 seconds; the bridge now waits 50 seconds at a time*) and tells the model after its next result.

**A call cut off loses nothing.** If the client gives up on a call (its own timeout, or you stop the model) while the bridge is waiting, and the model's turn opens just then, the model's next call returns that turn first (*Your call to stand_by was not run: your last call was cut off by the client before its result reached you, and that result comes first*) and is not itself run, so the model never answers a turn it has not read (playtest 3's lost question). A cut-off wait in which no turn opened is only noted after the next call's result. In the same way, if the model's turn opened while no call of its was waiting (its last call had come back *Still waiting*, and it had gone on in the chat), its next call returns that turn first (*Your call to ... was not run: this turn opened after your last result, and it comes first.*); and what was added to its open turn while it was reading comes with the result of its next call, so nothing the game sent goes unread.

**The token.** The game never sees the text of the chat, only the tool calls. So the token `FREESAIL-OPT-OUT` counts in any argument of any tool call, and the `opt_out` tool is always listed. If you ask the model in the chat to leave, it calls `opt_out` or passes the token on; the game is saved and the station released. This is a limit of the protocol, not a choice.

**When Claude Desktop closes** (or the chat's server is stopped), the bridge releases the station: the watcher is stood down *by the MCP bridge: the client disconnected*, and the game is saved. The game goes on without it.

**When the game is restarted** under a running client (package 37g), the bridge asks for its station again of itself: the model's next call is answered *Your call to ... was not run: the game holds no station for this door any more (it was restarted, or another game was started in its place). The bridge has asked for the station again, and the harness's brief comes first.*, with the brief, and the call after that runs. Until this package every call failed the same way until the client was restarted. If the restarted game was loaded from a save, the station is the save's: taken up again if this model held it, taken again by the one rule if it had been released (section 13).

**A new chat** in the same Claude Desktop session uses the same bridge and the same station; the model in the new chat has not read the brief, so start it with the prompt `brief` (the *+* menu, *freesail*, *brief*), which puts the brief as it stands into the chat.

## 4. Claude Code in the Desktop app

Claude Code reads a file named `.mcp.json` at the top of the folder it is opened on, and the gate folder has one, pointing at the same bridge by its module name, so it works from whichever folder you extracted:

```json
{
  "mcpServers": {
    "freesail": {
      "command": "py",
      "args": [
        "-m", "freesail.agents.mcp_server",
        "--game", "http://localhost:8000",
        "--model-name", "SET THE MODEL'S EXACT NAME HERE"
      ],
      "env": { "PYTHONUTF8": "1" }
    }
  }
}
```

1. **Set the model's name.** Open `.mcp.json` in Notepad and replace `SET THE MODEL'S EXACT NAME HERE` with the model you use in Claude Code, exactly as Claude Code names it (its model menu, or `/model`). Until you do, every call is answered "No station is offered: the bridge was started without the model's name", and no record is written under the placeholder.
2. **Start your game** in the browser (section 2).
3. **Open the gate folder in Claude Code** in the Desktop app (the *Code* tab; choose the folder `<the folder you extracted the gate zip into>`). The first time, Claude Code asks whether to use the MCP servers the project's `.mcp.json` names: allow `freesail`. `/mcp` in the prompt lists it with its tools.
4. **Play** as with Claude Desktop (section 3): ask it to connect and keep watch; the consent brief comes first for a name with no record; sail in the browser; `ask the watcher ...` in the order box. The bridge's two prompts appear as slash commands: `/mcp__freesail__brief` and `/mcp__freesail__keep_watch` (type `/` and look for *freesail* if the form has moved).

This file's shape is Claude Code's project configuration as documented when it was written; if Claude Code does not pick it up, check `claude mcp --help` (or Claude Code's documentation on MCP) for where project servers are kept now, and report it.

## 5. A local model under llama-server

`llama-server` comes with llama.cpp. Take the Windows build for CUDA from the releases page of llama.cpp on GitHub (`ggml-org/llama.cpp`, *Releases*; the zip whose name has `win-cuda` and `x64` in it, and the `cudart` zip beside it if the server complains of a missing CUDA library), unzip it anywhere, and open a terminal in that folder. Then, for a GGUF file on a 4090:

```
llama-server.exe -m C:/models/YOUR-MODEL.gguf --ctx-size 16384 --n-gpu-layers 99 --parallel 1 --jinja --seed 7 --host 127.0.0.1 --port 8080
```

- `-m` the GGUF file. Its name is what the consent record is kept under (the name only, never its folder), so the same weights under another file name are asked again, and a different quantisation is a different model.
- `--ctx-size 16384` the context. The watcher's brief is about 1,630 tokens, the tool definitions about 1,270, the consent brief about 1,480, and each glass's turn about 450 (measured on the frigate at seed 7 for package 28d, the shelf; four characters to a token), and the runner keeps the reply budget of 4,096 free (below), so 16,384 holds the brief and some twenty glasses before the runner starts leaving out the oldest turns; 8,192 holds two or three. A library read now costs what it serves (a section of the primer is a few hundred tokens, a whole chapter up to about 9,710), and a book the model shelves costs its one line from then on. A turn that grew while the model was thinking (things added to it) is longer. If the model does not fit in the card's 24 GB with it, lower this first.
- `--n-gpu-layers 99` puts every layer on the card (any number above the model's layer count means all of them). If the card runs out of memory, lower it: the rest run on the processor, more slowly.
- `--parallel 1` one conversation at a time, so the whole context is the watcher's (the server divides the context among its slots).
- `--jinja` uses the model's own chat template, which is what makes tool calling work. Without it the model cannot call `readings`, `answer` or any tool.
- `--seed 7` the default sampling seed; the runner sends its own with every request when you give it `--seed`.
- `--host 127.0.0.1 --port 8080` only this machine can reach it; the runner's default address.

These are the flags as llama.cpp's server documents them at the time of writing; if one is refused, `llama-server.exe --help` lists the current names. When it is up, `http://127.0.0.1:8080/props` in a browser shows what it loaded (`model_path`). A thinking model's reasoning comes back apart from its reply under llama-server's default reasoning format; leave that as it is (see section 12).

**The runner.** Start your game in the browser (section 2). Then, in a second terminal in the gate folder:

```
py -m freesail.agents.local --game http://localhost:8000 --endpoint http://127.0.0.1:8080 --seed 7
```

It reads which weights the server loaded and says so (`The model server serves <the file's name>.`), then asks the game for the watcher's station under that name. With no record for them, the consent brief comes first; the runner's terminal shows what the model writes (`model> ...`), and when it writes something without answering, the run waits at `owner>` for your reply (type it; a blank line sends it; a blank reply stops the step without a record). An answer of *yes, with conditions* with nothing after it is asked for the conditions once more. **After the answer, you have a turn at `owner>`** before the record closes: the runner shows the answer (`The model has answered (yes): ...`), and anything you type goes to the model, which may reply once, and both are kept in the record; a blank line at once closes the record. Its answer is recorded by the game in `docs/agents/consent/`. A yes goes on to the station; anything else stops the run with the reason and exit code 5.

At the station, the runner keeps going on its own: it asks the game for the watcher's next turn, sends it to the model, and hands the model's reply back, and prints a line for each turn (`== Morning watch, 1 bell (04:30): a turn, the glass ==`) and what the model says (`model> ...`). You play in the browser: the watcher's lines are in its log, and `ask the watcher ...`, `show the watcher's journal`, `stand down the watcher` go in the order box. When the station is released (the token, `stand down the watcher`, the welfare stop), the runner says so and ends with exit code 3.

Other flags: `--session test` (the brief says it is a test session rather than play), `--temperature 0.7`, `--seed 11` (the sampling seed), `--ctx 16384` (the context to budget against, if the server does not report it), `--max-reply 4096` (the reply budget, below), `--model NAME` (where the server serves several), `--ask-again`, `--handover-reserve 30000` or `--handover-reserve 0.3` (the officer's station: how much of the context is kept free when the harness asks for the handover note, in tokens or as a share of the context; below, and section 13).

**Pictures at the local runner** (package 45c, the owner's note 14 of gate m6a-2). The chart and the ship's view (section 16) are offered at this door too when the model reads an image: `--pictures auto` (the default) asks the server (llama-server's `/props`, its `modalities` with `vision`; Ollama's `/api/show`, its `capabilities` with `vision`), `--pictures yes` declares it (a server that does not say), `--pictures no` leaves them out. Offered, the picture goes to the model as an image part beside the tool's result, drawn by the open browser page as at the other doors; not offered, the tools' words are as before.

**The reply budget and the timeout.** Every request to the model server carries a reply budget, `max_tokens`, 4,096 tokens unless `--max-reply` says otherwise (the owner's ruling, 2026-09-28: generous, so that a long answer, a journal note or a thinking model's reasoning is never cut; a runaway is still stopped within about a minute and a half on a 4090). A request that has not answered in ten minutes (`--request-timeout` changes it) is given up: the runner prints `The model server did not answer within 600 s; the sample is left open. (1 of 3; asking again)`, reads the game again (anything that happened meanwhile, your question included, is added to the model's open turn) and asks again. Three failures in a row stand the watcher down with the reason, and the game saves. The timeout is long on purpose: a thinking model writing a long note can run to the whole reply budget, and a 27B model at four bits on a 4090 takes three minutes and more to generate 4,096 tokens after reading a long prompt; playtest 6 (Qwen3.8 27B) lost its farewell to a three-minute timeout. The budget bounds a reply; the timeout is only for a server that has hung.

**A reply cut off is asked for again** (package 37i). The runner reads why each reply ended, as the server says it (`finish_reason` at llama-server and at Ollama's `/v1` endpoint, `done_reason` in Ollama's own form). A thinking model can spend the whole reply budget thinking and come back with no words and no call: game 10's officer lost one reply in twenty that way, each passed on as an empty turn with no word to anyone. Now such a reply, and any reply with no words and no call, is asked for once more in the same request, with the reason said at its end in the runner's own words (*From the local runner, not the game: your last reply was cut off at the reply limit (4,096 tokens) while you were still thinking ...*), and the runner's terminal says so (*The model's reply was cut off at the reply limit (4,096 tokens) while it was still thinking; it is asked once more, with the reason.*). If that one is cut off or empty too, the terminal says so, the turn ends with nothing done, and the station's journal says why (`No reply reached the game through the local runner: ...`, of the kind `agent.cut_off`); nothing is said in the log, and the turn counts as one in which nothing was said, as an empty reply did. If it happens often, raise `--max-reply` (below).

**Tokens are counted by the server** (package 37i). Every reply carries the tokens the server counted for the request and for the reply (`usage` at llama-server and at Ollama's `/v1`; `prompt_eval_count` and `eval_count` in Ollama's own form). From the first reply on the runner measures each message by them: it keeps the ratio of the server's count to its own four-characters-a-token measure of what it sent, and scales by it. Four characters a token stands alone only until the first reply, and in the context check before stationing; in game 10 it ran 12 to 17 per cent short. The server's count also goes to the game with each reply, and the harness measures the officer's conversation by it (the larger of that and its own four-character count) when it decides to ask for the handover note. A count under half the runner's own measure is taken for a partial one (a server counting only what it had not cached) and not used.

**The handover's reserve** (packages 37g and 37i). For the officer's station the harness asks for the handover note when the conversation, by the server's count, has left less than a reserve of the context, and never before six tenths of it. The reserve is three tenths of the context and never less than 14,000 tokens, the larger, unless you give `--handover-reserve`: in tokens (`30000`) or as a share of the context (`0.3`, or `30%`); given twice, once in each form, the larger counts. The runner prints where the ask will come: *The handover note is asked for when the conversation, by the server's own count, has left less than 30,720 of the 102,400 tokens (...), and never before 0.6 of them: at about 71,680.* At 102,400 that is 71,680 (37g's 14,000 by the four-character count asked at 88,400, which by the server's count was past the ceiling); at 65,536, 45,875; at 32,768 the six tenths, 19,660.

**A request refused for its size** (package 37i). When llama-server refuses a request because it does not fit its context (*the request exceeds the available context size*), the runner reads the server's count of the request from the refusal, measures by it, leaves out the oldest exchanges that are not the brief, the handover note or the latest sample, says so once at its terminal (*The model server refused the request for its size (103,679 tokens by its count; the context is 102,400). The oldest exchanges are left out ...*), and asks again at once. It never sends the same request again; if the server refuses three smaller requests in one turn, or there is nothing more to leave out, the station is stood down with the numbers. (Game 10's two seatings both ended on the same request sent three times.) Ollama does not refuse a request for its size: it cuts the conversation itself (its log says `truncating input prompt`), which is why the runner's own budget now goes by the server's count, and why the context check wants a context size.

**For a long watch** (the review of gate 5c, part K's two settings, tried on the fake server in `tests/test_local_runner.py`). A model that thinks for longer than the reply budget is cut off every time at the default, and answers with `--max-reply 8192`; a larger budget is kept free of the context for every request, so the check and the budget leave that much less for the conversation. `--handover-reserve 30000` at 102,400 had the note asked for, by the four-character count alone, when the server's count stood at about 85,400, some 17,000 under the ceiling, where 37g's 14,000 asked for it at about 103,200, past it; with the server's count and the default reserve this build asks at about 72,000. Neither setting is needed now, but either may be given.

**The context check.** Before it asks the game for the station, the runner asks the model server what context it gives the model (`/props` for llama-server; `/api/ps`, or the model's `num_ctx` from `/api/show`, for Ollama) and measures what the station needs (the brief and the tool definitions, counted at four characters a token, a turn, and the reply budget). If the context is smaller it stops before anything is asked, saying both numbers and how to raise it; otherwise it prints `The context is enough: ...`. If the server does not say (an Ollama model not yet loaded), it says so, and `--ctx` is your word for it. **For the officer's station the check is stricter** (package 37g): the brief measured is the officer's own, which is longer than the consent brief the check was written against, and when the server does not say what context it gives and no `--ctx` is given, the officer is not seated at all (*the officer of the watch is not seated without a context size*): with none the harness can neither ask for the handover note in time nor leave out old turns, and the server cuts the conversation unseen.

**The context budget, measured.** How large a `--ctx-size` your card holds depends on the model: its weights, and its cache of keys and values, which grows with every token of the context. `tools/context_budget.py` reads the model file's header and works it out:

```
py tools/context_budget.py C:/models/YOUR-MODEL.gguf --vram 24 --headroom 1.5
```

It prints the model's layers, key-value heads and head width, the weights' size (the file on disk), the cache a token at f16 (llama-server's default) and at q8_0 (`--cache-type-k q8_0 --cache-type-v q8_0`, about half, which llama.cpp gives the value cache only with flash attention, `-fa`), and the largest `--ctx-size` that fits: the card's memory (`--vram`, in GiB; a 4090 is 24) less the weights and less a headroom you set (`--headroom`, 1.5 GiB by default, for the CUDA context, llama.cpp's working buffers and the desktop). The formula is in the script's opening words with its sources: two tensors a layer, times the key-value heads, times the head width, times two bytes at f16. A model with a sliding window (some of its layers attend only to the last few thousand tokens) keeps those layers' cache small unless llama-server is started with `--swa-full`; the script prints the figure with every layer at the whole context (an upper bound) and, where the header says which layers slide, the figure with those at their window, which is the one to go by. Where the header gives the window but not the layers, it says so, and `--swa-every N` (every N-th layer attends to the whole context, from the model's card) gives it. If the weights and the headroom alone do not fit, it says so with the numbers.

**The check.** The owner's observed range for the 26B and 27B models on the 4090 is **80k to 110k tokens** of context in practice (2026-09-28, anecdotal, from Hermes Agent sessions). The script's figures are to be checked against it: a figure far below the range probably means the sessions ran with a q8_0 cache or a sliding window the script was not told of, and one far above it that the headroom is too small; say which in the last column.

**The shelf: what the model keeps in its context.** The library is served in pieces with their sizes, so a local model reads what it needs and not a chapter at a time: `library()` lists the topics and what each costs, `library(topic='primer 3')` a chapter's sections with theirs, `section='reefing'` one section, `find='goose-wing'` the paragraphs that match. Every read is a *book* with a number (`primer 3, reefing, opened 04:10; book 7`), and the model puts it back with `shelve`: from its next request the runner sends that result as its one line (`You read primer 3, reefing, at 04:10; shelved (book 7). library(...) opens it again.`), so the pages are really gone from the model's context. A book left open goes back by itself after three more of the model's turns, and the next turn says so; **a picture never does** (package 45c, the owner's notes 2 and 4 of gate m6a-2): it stays in the conversation until the model shelves it, and `shelve` takes a note of what it showed (`shelve(book=3, note='the Manacles on the quarter, her sails full')`), kept on the picture's line with the time it was drawn, so that a model reading its own history finds what it saw in its own words; the brief tells it to write in its journal before it shelves one. Nothing leaves the library: any book opens again on request, and the brief tells the model its journal is where to keep what it took from a page.

If the model server is not running, the runner says `Could not reach the model server at http://127.0.0.1:8080: the connection was refused ...` and stops. If the game is not running, it says `Could not reach the game at http://localhost:8000 ...` and stops. If the model server fails in the middle of a watch (three failed requests in a row, or a refusal for size it cannot mend), the runner prints why and releases the station, and the game saves.

## 6. Ollama

Ollama speaks the same language on its own port, so the runner works against it unchanged; it is the quicker look, and `llama-server` is the exact one. The model's name is the one `ollama list` shows:

```
py -m freesail.agents.local --game http://localhost:8000 --endpoint http://127.0.0.1:11434 --model NAME-FROM-OLLAMA-LIST
```

The consent record is kept under that name with the digest Ollama reports for it, so a re-pulled or re-quantised model is asked again.

**The context.** A default Ollama install gives a model a small context and cuts the conversation to it without saying so. The runner's context check (section 5) catches it before anything is asked. To raise it, set `OLLAMA_CONTEXT_LENGTH` (for example `16384`) before starting `ollama serve`, or put a `PARAMETER num_ctx 16384` line in the model's Modelfile; with the context set large (the owner's Ollama runs every model at 262,144 tokens) the check passes and says so.

**A request that never ends.** If the runner seems stuck while the card stays busy for minutes on end, it is a **runaway generation**: the model has fallen into repeating itself and, with no limit, generates without end, since Ollama's own default reply length is unlimited. Playtest 4 was one: the harness of that build returned each `stand_by` as a tool result and asked the model again (a turn ended only on a reply with no tool call), so the model stood by thirteen times in a turn that never closed, and the last of those requests ran to 76,674 tokens before Ollama gave it up at ten minutes; the captain's questions and the glass meanwhile went into that open turn and were never answered. Now a stand-by ends the turn at once (section 2, *Standing by*), and the runner's reply budget (`--max-reply`, 4,096 tokens by default) bounds any runaway within about a minute and a half on a 4090; its timeout gives up a request after ten minutes, says so (`The model server did not answer within 600 s; the sample is left open.`) and asks again. Two things to check:

- `ollama ps` in a terminal: the model loaded, its context (`CONTEXT`), and whether it is on the card (`PROCESSOR`, `100% GPU`).
- Ollama's server log, `%LOCALAPPDATA%\Ollama\server.log`: its request lines (`[GIN] ... | POST "/v1/chat/completions"`) give each request's status and how long it took, so a runaway shows as a request of minutes where the others took seconds, and near it a cancelled request with a large `n_tokens`; a line with `truncating input prompt` means instead that the context is too small for the conversation (raise it, above).

## 7. The console instead of the browser

The console hosts the same connection for the doors on a port of its own:

```
py -m freesail.ui.console data/ships/frigate-36.yaml --seed 7 --wind 0,15 --heading 180 --agents-port 8000
```

It prints `A model's door connects to http://localhost:8000`. The doors connect with the same `--game http://localhost:8000` (so the configurations above are unchanged, as long as the browser game is not running on the same port). `state` prints the station's line (`The watcher (<name>, through the local runner): stationed; its turn is open.`), and the watcher's lines print in the log as every line does. The console's own flags `--lockstep`, `--consent-records DIR` and `--saves DIR` are as the browser game's.

**A save loaded to an earlier tick** (package 45c, the owner's note 3 of gate m6a-2): `--load SAVE --until TICK`, at the console and the browser's server alike, replays the save by its acts to that tick and hands the game over there, the stations free to be seated again; the log says it was loaded short of its end, and a tick beyond the save's end, or `--until` without `--load`, is refused in words. The browser's order box answers `state`, `muster`, `the sail room` and `the booms` as the console does (package 45c), a line for you that is not the log's.

## 8. `--lockstep`: the game waits for the model

Either game takes `--lockstep`: then the clock **holds while the model has its turn** and runs on when it hands the turn back. It is for testing at 1x (the model is never behind), and for competitive play later. The instruments' *Clock* row says `running at 1x, waiting for the watcher` while it waits, and `tick 600` in the order box stops at the watcher's next turn. Without `--lockstep`, the game does not wait: what happens while the model thinks is added to its turn. The REPL and the tests always run in lockstep.

## 11. How to stop

- **`stand down the watcher`** in the order box (or at the console). The game is saved, the journal says why. The door is told at its next call. The station may be taken again, by the same model or by another (section 13).
- **The model stands down** (package 37g): the `stand_down` tool, at any station, with a note for whoever sits there next; with the deck the note is the watch's handover note and is asked for, and a stand-down without one is not made (package 37l); without the deck it may be left out, and the result says none was left. The game is saved, the note is in the log and the journal, and the station is released to be taken again. It is the amicable way to end a session, and it is not a withdrawal: no consent question follows it.
- **The token.** The model writes `FREESAIL-OPT-OUT` anywhere in a reply (over MCP: in any tool argument, or calls `opt_out`). The game is saved and the station released at once, whatever else the reply said, whether or not it was the model's turn. This is a withdrawal: before that model is seated again in the same game the consent question is put to it again, with the reason it gave, and a no then is kept; `opt_out` with `final=true` bars that model from the game, at any station, and the station stays open to another.
- **Close the door.** Quit Claude Desktop, close Claude Code, or press Ctrl-C in the runner's terminal: the door releases the station, the game saves, and you sail on.
- **Stop llama-server** with Ctrl-C in its own terminal: the runner then releases the station, saying the model server could not be used.
- If the harness sees the watcher stuck (the same order three times with nothing changing, or its turn left open with no reply for a watch of ship's time), it nudges, then pauses and asks you in the log and in the instruments (`resume the watcher` or `stand down the watcher`), and only if nobody answers within ten real minutes, however fast the ship's clock runs, does it stand the watcher down itself. The minutes are the game's own clock's, counted whether the ship's clock runs or is stopped (package 31c, the owner's ruling of 2026-09-30: until then a watch of ship's time stood it down too, whichever came first, and at 300x a watch is under a minute). At the REPL, where nobody at the door answers a pause (the terminal is the station's), the clock holds while it is paused and the ten minutes decide.

## 12. What the harness does not do

- **No other door's calls run under a seated model's name** (package 37g). Stationing gives the door a key to that seating, and every call that reads, speaks, orders or releases for the station carries it; a call without it is refused (*The station of the watcher is held by ..., through the MCP bridge (stationed); this call carries no key to that seating, and nothing was run.*). When the same model's door is started again (a client restarted, or a second client for the same name), the newest door holds the seat, the older is refused at its next call and stops, and the log says *The door behind the watcher changes: ... takes up the station again through the MCP bridge, and the door that held it before is no longer answered.* A station that is held is taken by no other model: stand it down first.
- **Over MCP the chat is invisible to the game.** The token counts only in tool calls; the consent record holds what the game saw; the bridge cannot tell which model the chat uses (you name it).
- **Over MCP (and at the REPL) shelving cannot take pages back.** The conversation is the client's (or what the terminal printed), so `shelve` notes the book, the game never shows its pages again, and the result says plainly that the client keeps its own copy. Claude's own window keeps itself; the journal carries the habit.
- **Reasoning is not scanned.** A model server that returns a thinking model's reasoning apart from its reply (llama-server's default) keeps it out of the token scan: thinking about the token does not use it, writing it does. The consent brief says so, and the consent record keeps the reasoning verbatim in a section of its own. If the server is set to put the reasoning inside the reply instead, it is scanned with the reply.
- **The game does not wait** for a model unless you start it with `--lockstep`. A slow model's turn grows while it thinks; nothing is lost, and the watcher is judged by ship's time, not by how long it takes to type.
- **A save is exact from its checkpoint; a save of package 42 or later replays on any build** (package 37d; package 42, section 16). Beside every save lies its checkpoint, the whole game as it stood, and `--load` takes the game up from it at once; the terminal says which road was taken and the log's digest. Every save and checkpoint is stamped with the build that wrote it. A station's orders are not in the journal, so a replay hands its recorded replies back wherever the rules of the build that replays open a sample: under another build that is a different game. When the checkpoint is missing, is not that save's or cannot be read, a save written by another build that holds a station's transcript is therefore **not** replayed: the terminal says which build wrote it, which build this is, why the checkpoint was not used and that a replay would not be the game that was played. `--replay-anyway` (on the server, the console and its `replay`, and the REPL door) replays it all the same, as another game from the same beginning. Keep each build's saves with their checkpoints in that build's folder. **Since package 42 that is a save of before only**: everything a station puts into the game (its seating, its orders, its words in the log, its journal, the deck and its stand-by as they stand) is journaled at its tick as the game's input, as your orders are, and a save of another build is replayed by those acts, each at its tick whatever that build's sampling would ask; the terminal says so (*It was replayed by its stations' acts ...*). A save of the build that wrote it is still replayed from the transcript, which rebuilds the station's conversation as well, to the same log.
- **Every stop replays.** The model's replies are kept with the moment each came (the tick and how many of your orders came before it), and so are the stops that come from outside (a door closing, the token sent out of turn, the ten real minutes, a turn the runner could get no reply for), with how many inputs of every kind came before them: a replay of the save makes them at the same moments and gives the same log. A door's act is made between two of the game's ticks, and a replay makes it there too (package 37i: game 10's last save replayed one line short, because the runner's stand-down of the officer was made in the replay at a standing order's order inside the tick, before the harness had woken him).

## 13. The officer of the watch: a station with authority (packages 37 and 37g)

The officer of the watch is the first station that gives orders (`docs/primer/16-the-officer-of-the-watch.md` says what it may and may not; spec M5 §29). The model takes the place of one of the ship's own officers, the first lieutenant on the frigate, the mate on the schooner and the cutter, the lieutenant on the brig, and the log names him. **The station is asked for at the door with `--station officer`**, everything else as for the watcher:

- Claude Desktop or Claude Code: add `"--station", "officer"` to the `args` in the configuration (section 3 or 4), restart the client, and start the chat with the prompt `take_the_watch` (the *+* menu, *freesail*), or write *"Please connect to FreeSail as the officer of the watch and read what its harness sends you."*
- A local model: `py -m freesail.agents.local --game http://localhost:8000 --endpoint http://127.0.0.1:8080 --seed 7 --station officer`. The cutter is the owner's choice for a local model's watch (decision 30): start the game with `data/ships/cutter.yaml`, where the officer is the mate.
- The REPL: `py -m freesail.agents.repl data/ships/cutter.yaml --seed 7 --station officer --model-name "a name"` (or `--human`).

**Consent, again, and the drill.** The consent brief changed for this station in the sections that bear on what a model was told (`README.md`, the re-ask rule), so a model with a yes on record from before is asked again the first time it comes to any door after this build, whichever station it asks for: the game's terminal says `the consent brief has changed since their record (...) in the opening, What an instance would see and do, Leaving, Being stopped, The journal, which bear on what the model was told, so the question is put again`, and the brief comes first as it did the first time. After a yes, for the officer's station only, a short **drill** follows in the same conversation, as data: the model is asked to open a section of the library, write a line in its journal and stand by until a bell, three calls in up to four replies; a model that manages them is given the station brief, and its record says `Drill: passed`; one that cannot is thanked and stood down, its record says what was not done, and no station is offered until you ask again (`--ask-again`). A model whose record is a yes on the new brief but never drilled (a yes given at the watcher's station) runs the drill alone when it first asks for the officer's. The record's header now says which kind of identity it carries: the served file's name (the local runner), or the name you typed (Claude Desktop, Claude Code, the REPL). **Package 37g revised the brief once more** (2026-10-07), and you had it made leaner the same day, before any model was asked again: the consent brief now keeps the kind of thing a model is asked to agree to, and a station's particulars (which orders lie within it, what the harness counts and by what numbers) are in that station's own brief, where they may change as the game is built without the question being put again. Every model with a yes on record is asked again at its next seating: the terminal says `the consent brief has changed since their record (...) in What an instance would see and do, Leaving, Being stopped, The journal, which bear on what the model was told, so the question is put again`, and the question itself now tells the model why: *This question is put to you again because the consent brief has changed since this model's answer of ..., which was yes, in 4 sections that bear on what it was told: ...* (a record made against 37's brief names those four; an older one names the opening as well, which it already owed). For the officer's station the drill is run again with it. The package asked no model and wrote no record: the re-asks are yours to run.

**The deck is yours to give, and to take, as often as you like** (package 37g; your ruling of 5 October). When the model has its brief the log says `The officer of the watch takes the station (<name>, through ...); sampled every glass and on notable and urgent events.`, and the instruments' Stations row reads `The officer of the watch (<name>, through ...): stationed; the deck the captain's`. Seated without the deck it is what the watcher is: it reads, speaks, answers, keeps its journal and stands by, and every order it gives is refused (*The officer of the watch has not the deck*) until you type, in the order box:

```
you have the deck
```

(or `Mr Pearce, you have the deck`, with the officer's own name). The log says `Mr Pearce, you have the deck. The officer of the watch has the deck; the captain's standing orders are his night orders.`, the station's row reads `with the deck since ...`, and the officer's next turn carries your word, the book as it stands, everything your word allows him, and the last handover note in his journal. `I have the deck` takes it back **and no more**: `The captain has the deck. The officer of the watch stays at the station, off watch.` Nothing is saved and nobody is stood down; give it again whenever you like. It is also the plain way to take the con yourself: while you have the deck, any order of his is refused. The people's reading has him *on deck, with the watch* while he has the deck and *off watch* without it. Off watch he is sampled as he was before the deck was first given (every glass and on the notable and urgent lines), which on the frigate under plain sail is about a dozen samples and some four thousand tokens in a watch.

Before and during, `tell the officer ...` gives him your words and `ask the officer ...` a question; either, typed while his turn is open, breaks the stand-by that closes that turn, so he answers in his next sample and not after his wait. `the officer of the watch` (or `who has the deck`) at the prompt reads who has the deck, since when, what he was told and what you allowed. His orders appear in the log as his (`By the officer of the watch: taking in the royals.`), a refusal by his domain in words (`The officer of the watch may not tack ship without the captain: a manoeuvre ... is the captain's.`), and his standing orders in the book in his rank, the captain's standing over his where they cross. What he says is marked notable, with the deck or without. All hands he calls under your word are logged as his (*All hands! (by the officer of the watch's order)*).

**What your word allows him.** Within his domain without a word from you: sail, the yards, the lines, the lead and the log, bearings and fixes, the lookout and the pilot's hail. Beyond it, two kinds of word:

- **A named thing.** `you may tack ship if the land closes within two miles` allows the order, your condition kept in your words for him to judge. A grant means what it says: `you may shape a course for Falmouth` allows a course for Falmouth and for no other place (the log says so), `you may let go the best bower` that anchor; `you may shape a course` allows any. Several grants of one order stand together and the reading lists them all. `you may steer` is your word for the course by any of its orders (`come up half a point` and `steer 340` are judged alike). Words that would allow nothing are refused with the cure (`you may set the reckoning` reads as `set`; the refusal names `you may set the reckoning to`). `you may not tack ship` takes one back.
- **Your general authority**: `you may work the ship` (or `you have general authority`, `you have my authority`, with any words after it kept as you said them). Within it: the helm and the course along the passage, tacking, wearing, heaving to and filling away, sail, all hands and the watch below, the anchors and their cables, the sights, and a course shaped for a position at sea, a mark, or the place she is bound (the port, road or anchorage you last shaped a course for). **Kept back**, each refused in words that say so and may be allowed by name: the port's business (taking or declining a pilot, buying and selling, the purse, stores, the boat's errands ashore), your standing orders, a new destination, what cannot be undone, the reckoning set by hand and the tide allowed in it, a chase, and sending for a person. `you may not work the ship` takes it back, and what you allowed by name stands.

Either kind stands through the deck going to and fro, has force only while he has the deck, is said to him again in the sample that gives the deck, and ends when you take it back or he leaves the station. **To avoid an immediate danger** he may, with no word of yours, alter her course by any helm order (`helm a-lee`, `hard a-weather`, `bear away two points`, `steer NW`), heave to or let go an anchor, giving his reason; the log says it, notable: `The officer of the watch gave that order on his own word, to avoid an immediate danger (land close ahead on the larboard bow): heave to.`

**Three ways of stopping, which are not one another.**

- **The deck given back, and he stays**: your `I have the deck`, or his own `hand_over` with his handover note (said in the log, notable, and kept in his journal).
- **A stand-down**: your `stand down the officer`, or the model's own `stand_down` tool with a note for whoever sits there next. The game is saved and the station released; start the door again as before and the same model, or another with its own consent, takes it: `The officer of the watch takes the station again (<name>, through the local runner), relieving <the name before>: the third seating; it had ...`. No consent question is put to a model whose yes still stands. The new session's brief carries the last handover note whole and a line of the journal's size, and `read_journal` reads back what the holder before it wrote. What your word allowed ended when the station was left: say it again.
- **A withdrawal**: the token, or `opt_out`. Before that model is seated again in the game the consent question is put to it again, saying that an instance left and the reason it gave (a drill passed on record is carried, not put again); a no then is kept, and the question is not put again at each start. `opt_out` with `final=true` bars that model from the game, at any station; the station stays open to another. `final` is read from the tool's own setting only.

A game saved before package 37b that holds an opt-out has no record of how the station was left, and reads as a stand-down; by your answer of 5 October that is right for the one such save there is.

**The handover note.** Through the local runner, when the conversation, by the model server's own count, has left less than a reserve of the server's context free (three tenths of it and never less than 14,000 tokens, unless `--handover-reserve` says otherwise in tokens or as a share; and never before six tenths of the context; section 5), the harness asks for the note without taking the deck (`handover_note`): the model writes it, with the deck or off watch, and the older exchanges of its conversation are replaced by the note, the brief and its last turns kept whole. Claude through Desktop keeps its own window and is not asked; its journal gives it the habit by hand.

**What the harness watches for at this station** (the primer's chapter 16 and section 11 above):

- **Orders that undo one another**: *set, take in, set* on the same sail, hove to and filled away, an anchor let go and weighed. Three in a chain within a watch bring the nudge, with the result of the order that caused it; the chain going on after he has read it brings the pause with you asked, then the ten real minutes. Altering the course is never counted, however often, nor the next thing after the last. (The rule before this package spoke 42 times in the nine games and was right twice; on those 42 it is now silent.)
- **Silence**: no reply for an hour of ship's time; a call made inside an open turn counts as a reply.
- **A paused or silent officer does not keep the deck.** When he has given no reply for his hour and has been told so, the deck is yours until you give it again: `The officer of the watch has given no reply for an hour and has been told so; the deck is the captain's until he gives it again.` When he is paused: `The officer of the watch is paused (...); the deck is the captain's. Continue, stand down, or leave paused? ...`. Both lines are urgent and ease the clock to 1x. `resume the officer` gives the deck back as he held it (`... resumed by the captain; he has the deck again, as he held it since ...`); if you would rather keep it, say `I have the deck` first. His standing orders stay in the book throughout.
- **The stand-by with the deck** must name an event or a bell (an hour or a watch is refused). An urgent line wakes him, and so does a notable line that speaks of danger (an anchor dragging or still coming home, fog coming down, land or a sail closing, a spar or a line straining, an evolution failed, the ship taken aback or her sails lifting). A wait that cannot end is refused when he asks it (`six bells` in the last dog watch is answered with the bells that watch has; `the turn of the tide` under way with `the turn of the tide by the reckoning`). A wait for an event ends at the next eight bells and says so.
- **The turn's budget**: sixteen orders at a sampling point and thirty-two reads and notes, counted apart; `answer`, `say`, `opt_out`, `stand_down`, `hand_over` and `stand_by` always run. A call over a count is not run, and its result and the log say so (*... was not run: this turn's 16 orders are given.*).

**The lead's watch and the owner's** (spec M5 §29; decision 30). Gate 5c's verdict waits on an officer's watch by a model through each door beside the owner's own: an Opus 5.5 watch through Claude Desktop on one of the two passages (`--scenario data/scenarios/naval-cruise.yaml` or `merchant-passage.yaml`), a local model's on the cutter through the runner, and the lead's through Claude Code opened on the repository; each after its re-ask and its drill, each recorded on the officer's form (`docs/playtests/README.md`, the sections 5a to 5d).

## 14. The captain's station, and the player's seat (package 40)

The captain's station is the third station and the first with the player's whole surface (spec M6 §3; `docs/primer/17-the-captain.md`): every reading, every order at every level, the standing orders as his own book, the port's business, the people, the papers, and the deck to give to the officer and take back. The model takes the place of the person the ship's wardroom file binds the station to (`data/people/<ship>.yaml`: the captain of the frigate, the master of the schooner and the cutter, the commander of the brig-sloop), and the log names him. **The station is asked for at the door with `--station captain`**, everything else as for the officer:

- The desktop client or the code client (sections 3 and 4): add `"--station", "captain"` to the `args` in the configuration (section 3 or 4), restart the client, and start the chat with the prompt `take_command` (the *+* menu, *freesail*), or write *"Please connect to FreeSail as the captain and read what its harness sends you."*

- The REPL: `py -m freesail.agents.repl data/ships/topsail-schooner.yaml --seed 7 --station captain --model-name "a name"` (or `--human`).

**No model is seated here yet.** The station is a kind of thing the consent brief does not describe (a station with more authority than the officer's), so by your ruling of 7 October (decision 37) the question is put to every model again, once, with the brief revised for it; the package drafted that revision as `docs/playtests/drafts/consent-brief-m6-draft.md`, which you approved, and package 42a made it in `docs/agents/ConsentBrief.md` on 2026-10-09 with what 6b and 6c add described beside it, so that it is made once. His standing orders are the book; the book he inherits is the scenario's, and where the scenario gives the rules-based captain an intent (`intent:` in the scenario file; section 15 of the spec M6 §4, the merchant on `data/scenarios/merchant-intent.yaml`), the state's book (`the book 'on passage'`) is loaded in the book of standing orders by the rules and shown to him as his night orders, to keep, belay or write over. His brief head says the voyage first: the scenario's name, the intent or the book, the ship and her nation, the people aboard with their outlines, and the book as it stands. `the captain` (or `who commands`) at the prompt reads who holds the station, through which door, whose the deck is and what book he sails by; `the people` says who is in command.

**When his door is silent, the deck passes to his book**, and the rules-based captain's judgements stand in where the scenario gives him an intent (`The captain's door has given no reply for an hour and has been told so; the deck passes to his book; the rules-based captain's judgements stand in, until he gives an order again.`, urgent); on a scenario with a book and no intent the line says the standing orders hold the deck, and the passage goes on as it does with nobody seated (truth 79). His next order takes the deck back and says so (`The captain's door answers again (an order given); he has the deck, and his book stands as his night orders.`). `hand_over(note)` at this station lends the deck to the book with his note and keeps him at the station; his next order takes it back. A paused captain's station (`The captain is paused (...); the deck is his book's.`) is yours to resume (`resume the captain`) or stand down (`stand down the captain`). The three ways of stopping are the officer's: the deck lent and he stays; `stand_down` or your `stand down the captain`, with the game saved and the station open to be taken again, the rules holding her meanwhile; the token or `opt_out`.

**The officer under him.** From the captain's station the officer of the watch is given the deck, allowed things by name or in general, told and asked by the sentences you type (`you have the deck`, `you may tack ship if the land closes within two miles`, `you may work the ship`, `tell the officer ...`, `ask the officer ...`), through `submit_order`; the log says them as his (`By the captain: you have the deck.`). What the harness counts at this station is what it counts at the officer's, by the officer's numbers (section 13), since the orders are the same kind of thing; the stand-by with the deck wants an event or a bell, as the officer's does, the book holding the deck meanwhile.

**You are the owner at the door, whatever station you hold or none** (your ruling 1 of 2026-10-09, decision 39). The stop, the consent question and the drill, `you may` and `stand down` for any station, the save and the clock are yours, and your words reach a station as the owner's and never as another station's. Beside that, **you may take a station below the captain's yourself**, under a model captain or under the rules: the console and the browser seat you at the officer of the watch's station with

```

py -m freesail.ui.server --scenario data/scenarios/merchant-intent.yaml --seat officer
```

The log says `The player takes the officer of the watch's station (the player, through the console, at the officer of the watch's station); his orders are judged by the station's authority and the captain's word, and the deck is the captain's until he gives it.` An order you type is then judged exactly as a model's at that station would be (the officer's domain, the captain's named grants and his general authority, the way out of danger; section 13), refused in the same words (as a driver's line, so that a replay says it again), and given under the station's actor and journaled when it passes (`Order: set the royals.` by *the officer of the watch (the player)*; the people's lines say it was the officer's). The primer is your brief. A save made with you seated replays with you seated again (the seating is a driver's line in the inputs), and a checkpoint carries the seat. The seat is not a harness: nothing watches your welfare, there is no patience, and it is not among the stations a door can take (`the station of the officer of the watch is held by the player` is the refusal a door meets while you sit there; stand the seat down first).

## 15. The wardroom: the master's, the lookout's and a passenger's stations, the conversation, the pace (package 41)

Several models hold several stations on one ship at once, through several doors, with you or without you, under one clock (spec M6 §11 and §12; `docs/primer/19-the-wardroom.md`). Three stations join the three you have: **the master's**, **the lookout's** and **a passenger's**; the stations speak to one another; `you may` flows down the ranks; and the clock keeps a pace. No model is seated at any of them by this package: the fakes prove them (`tests/test_wardroom_doors.py`, truths 82 to 85), and your wardroom game is gate 6b's.

**The stations are the ship's, bound to her people.** Which stations a ship has, and which of her people holds each, is a binding on the game's world and no longer a list in the code (`the stations` in the order box lists it): the wardroom file's `stations:` (`data/people/<ship>.yaml`) is only its starting state, the master's station bound to the frigate's and the brig's master and to the schooner's and the cutter's mate, the lookout's to a hand at the masthead with no name, a passenger's to nobody until somebody comes aboard. A door asks for a station by its name there (`--station master`, `--station lookout`, `--station passenger`, beside `watcher`, `officer` and `captain`, at the MCP bridge, the local runner and the REPL; the flag takes any name aboard, and the game refuses one the ship has not got, naming the ones she has). A station bound to another person builds its brief from that person's own outline (his rank, his station aboard, his history); a station unbound while a model holds it releases that model with a line saying why, as `stand down` does, and a door asking for it afterwards is refused. The two operations are the game's (`world.stations.bind`, `unbind`); the order that drives them from the director's chair, `person: "Mr Fox" comes aboard as master`, is milestone 7b's and nothing of it is here.

**A station's kind and its holder** (package 45c, the groundwork for stations that multiply). The file's `stations:` takes a kind beside the holder where the station's name is not its kind's (`second officer: {kind: officer of the watch, holder: second lieutenant}` on the frigate): a door seats it by its name (`--station "second officer"`), its brief and its authority are the kind's, and its journal (the station's durable memory) is the person's, not the station name's, so that a person moved to another station keeps his own and two of one kind keep theirs apart. **The lookout unheld**: `ask the lookout` and `tell the lookout` with nobody at the lookout's station are answered by the ship's own masthead from the readings, by the rules, as its hails are.

**The master's station** works the ship's reckoning when the ship's own master would: at noon, at a fix by cross bearings, and at your word (`work up the reckoning`). At each the model is sampled with the master's slate in its sample's notice (the slate of section 14's `work my reckoning`, with the noon's observation as the ship took it), works it and gives its figure with `my reckoning is <position>`; a figure within thirty minutes of the working (the time the ship's own master is below at the day's work) **is the ship's account**, said in the log with whose it was (*The master's figure is the ship's account: ... worked at the master's station by Mr Harvey (<the model>, through the local runner)*); none within that time and the ship's master's figure stands, said in the log too. A figure at any other time is the station's own reckoning beside the master's, as the officer's is. His domain is the reckoning, the sights, the lead and the chart's queries, and no order of the deck; there is no deck at his station, so no `you have the deck` and nothing to hand over; a named thing may be allowed him with his station or his name before the comma (`master, you may heave to`, `Mr Harvey, you may heave to`), by you or by the captain's station. `the master` reads the ship's master and, when the station is held, who holds it and the working open for him.

**The lookout's station**, for a small model: it sees what the masthead sees (the sightings as the game makes them, `what is in sight`, `the nearest land`) and hails the deck (`hail sail ho, two points on the larboard bow`, or any words said at the station): a notable line from the masthead, heard by whoever is on deck, which wakes an officer with the deck who stands by, as a line that speaks of danger does. Its one other order is `make her out`, and `the glass on <ship>` (package 56: what the glass shows of a near ship's manoeuvre and work by the tiers of her distance, a reading every station may ask); everything else is refused in words. Its cadence is the masthead's lines, an urgent line and each glass, never the quarterdeck's notable lines (so a say on the quarterdeck is not heard aloft) and never the minute. `the lookout` (or `who is at the masthead`) reads who holds it, what is in sight and its last hail.

**A passenger's station** is a person aboard with no duty: a model (or you, `--seat passenger`) reads, keeps a journal, speaks and asks, answers a question put to it, and leaves; every order of the ship's is refused in words. The consent brief covers it in kind already (the watcher's authority or less), so no question is put again for it.

**The deck's conversation.** A station addresses another by its station or by its person's name or role, and the words are a log line with where the speaker stood and who heard him, carried in the hearer's next sample under the speaker's name, never as the operator's: `say <words>` is heard by whoever stands where the speaker does (the quarterdeck is the captain's, the officer's, the master's and a passenger's; the cabin the captain's gone below; the masthead the lookout's) and rides the hearer's next sample as `heard`, with no sample forced; `tell the master <words>` and `tell the first lieutenant to shorten sail` reach the station as your `tell` does, under the speaker's name and place (*The captain (Mr Bowen), on the quarterdeck, to the officer of the watch: ...*); `ask the master for a course` puts the question, whose answer comes back to the asker as a word, and the asker is told once when none comes within the asked station's patience. A `say` of yours in the order box is the captain's, on the quarterdeck; `ask the master <reading>` with nobody at the master's station is still the reading's own form, answered at once. At your seat, `say`, `tell` and `ask` are your station's; the owner's sentences stay yours.

**Who may give what.** `you may` flows down the ranks: you to any station, the captain's station to the officer's and the master's (`master, you may wear ship` through its `submit_order`), nobody upward; the officer and the master may give no station's sentence but the conversation's. A station's `stand_down` is its own; `stand down the <station>` is yours and the captain's. **On an intent scenario with nobody at the captain's station**, a model or you at the officer's station is given the deck by the rules-based captain's own words at his judgement, his book over it (*Mr Pearce, you have the deck. ... (Mr Travers, by his rule, on passage; his standing orders stand over it.)*), and he takes it back, saying so, for a judgement that needs the deck (the gale and the shelter, a stranger investigated, chased or evaded, distress), giving it again in a quiet state. **Your seat** takes the lesser stations too: `--seat master`, `--seat lookout`, `--seat passenger` beside `--seat officer`, each with its station's authority and no deck.

**The stand-by on several conditions.** `stand_by(until='eight bells, or a sail sighted, or the true wind exceeds 30 knots')` takes several conditions joined with *or*, each in the standing dialect's own words (an event, a bell, an interval, or a reading's condition the book could read: `the land is in sight`, `the true wind exceeds 30 knots`); any one of them wakes the station, and the sample that wakes it names which (*The true wind exceeds 30 knots (one of: eight bells, or a sail sighted, or ...)*). A condition the dialect cannot read is refused in its own words, with the cure. The dialect's one *or* inside a condition (`the true wind veers 1 point or backs 1 point`) still reads as one. A wait with the deck for an event still ends at the next eight bells.

**The pace rule, the default** (spec M6 §12; your ruling 2 of 9 October). The clock slows to 1x while any model's sample is open, whoever holds it, at whatever station, and runs at the set compression again when every open sample has been answered or has stood by. It is not lockstep: the ship sails on at her own second while the model thinks, and a slow answer lands late; `--lockstep` holds the clock for a door with the floor and stays the separate option; `--free-running` runs at the set compression with no slowing, the flag for the solo player who wants a model to think while he sails at sixty times. The rule moves no tick of the world, only how many a real second brings, so every recorded passage replays to its digest under any of the three. The instruments' *Clock* row and `state` say the pace; `the pace` in the order box reads the set compression, the rule, which samples are open and since when; the log says once, as a driver's line, when the clock has been held at 1x for a station longer than two real minutes (*The clock has been held at 1x for the captain for 120 real seconds; its sample has been open since ...*), so that a slow door is seen and not suffered. **Each station's cadence** is a setting of its seating, said in its brief: `--cadence glass` (every glass and on the notable and urgent events, the default), `--cadence watch`, or `--cadence events` (on events only), the station's own lines kept whatever it is; so a lookout on a small model is not sampled as often as the captain. The pace truth of M5 §30 measured with three stations sampled at a glass each is in the tuning notes under package 41.

**Three stations through three doors, and the save.** A second door asking for a held station is refused in words, as before; a station is found by its name and its key. A game with three stations seated (two models' and your seat) saves and loads from its checkpoint with all three, each re-seated station reading its own journal and its brief carrying the journal's size; the replay of such a game on a build whose sampling differs is package 42's transcript-driven replay.

## 16. The API door: a model through its own API (package 42)

The fourth door calls the model through its maker's own API, the Anthropic Messages API, with no chat client between: the game is in your browser window as always, and the door runs in a second terminal, asks the API for the model's replies and hands them to the game. The consent brief already names this kind of session (package 42a): you are at the door, the key is yours and in nothing the game sends, writes or saves. Everything else is as at the local runner (section 5): the consent question first with your word at `owner>`, the station's brief, the turns, the three ways of stopping, the journal, the handover note.

**Once: install and put the key in your machine's credential store.**

```
py -m pip install -e ".[dev,server,agents]"
py -m freesail.agents.api --store-key
```

The second asks for the key without showing it as you type and puts it in Windows' own credential store (the Credential Manager, *Windows Credentials*, a generic credential named for `freesail`; on a Mac the Keychain, on Linux the Secret Service), under the service `freesail` and the account `anthropic-api`. Nothing else is written anywhere. Take a key from the API's console page for keys; to change it, run `--store-key` again; to remove it, delete that credential in the Credential Manager. The door reads the key from there first. **For a machine with no store**, set the environment variable `FREESAIL_API_KEY` (or the SDK's own `ANTHROPIC_API_KEY`) in the terminal before starting the door, or name a file with `--key-file C:/somewhere/outside/the-key.txt`, outside the game's folder. The game never reads a key from a file of its own settings, and never writes one.

**Each game: start the game, then the door.**

```
py -m freesail.ui.server data/ships/cutter.yaml --seed 7
py -m freesail.agents.api --game http://localhost:8000 --model "THE MODEL'S NAME, AS THE API NAMES IT" --station officer --effort high
```

- `--model` has no default: the repository names no model, and the choice is yours. The door asks the API what that name is before anything else, and the name the API reports is the one the consent record is kept under (`The API serves ...`), with the context the API gives it, which the game uses for the handover note. If the API ever answers with another model than the one seated (a fallback of the server's), its reply is not passed on and the station is stood down with the reason: consent is per model. The door never asks for a fallback.
- `--station` by its name aboard (`watcher`, `officer`, `captain`, `master`, `lookout`, a passenger's; section 15), and `--cadence glass|watch|events`, as at every door; `--session test` for a test session; `--ask-again`; `--handover-reserve` as at the runner.
- `--effort low|medium|high|xhigh|max` sets how hard the model thinks (the API's effort). Without it the model's own default stands. The current models think as they judge (adaptive thinking) and cannot be told not to think at all, so there is no "off".
- `--max-reply` (16,000 tokens by default, thinking included) bounds one reply; `--request-timeout` (600 seconds) one request. Every request is streamed, so a long reply never times out.
- `--base-url` points the door at another address, a proxy of yours (the tests point it at a small server of their own); `--exchanges FILE` writes every request's body and every reply's, never a header, one line each, to a file of yours, so that you can read exactly what was sent.

**What the door sends each turn.** The station's brief (as the system prompt), the tools' definitions, and the conversation since the brief: each sample as the game made it, the results of the model's calls, and the model's own earlier replies as the API gave them (its thinking with them, so that it keeps its reasoning); the reply budget; the effort if you gave one. The brief and the tools are marked for the API's cache, and so is the conversation up to its last part, so each turn pays in full only for what is new since the last (cache reads are a tenth of the price). Nothing else: no name of yours, no folder, no telemetry. The key goes in the request's header, set by the SDK, and nowhere else.

**What it costs, and how it says so.** Every reply carries the API's own count of what it used, and the door keeps them. At each handover, and when the station is released, the door's terminal says it: *The API reported, in all, for 42 requests: 312,400 tokens in (280,100 read from the cache, 12,600 written to it, 19,700 not cached) and 9,850 tokens out.* Multiply by the API's prices for the model to have the cost; the cached tokens are the cheap ones. The count goes to the game with each reply too, which measures the conversation by it for the handover note.

**A reply cut off at the reply limit**, with a call in it or no words, is asked for once more with the reason said, as at the runner (section 5); cut off again, the turn ends with nothing done and the journal says why. **A reply the API's safeguards decline** is not asked again: the turn ends with nothing done, and the journal says so with the reason the API gave.

**The door will not start** when the key would be written somewhere the game keeps things: a `--key-file` inside the game's folder (where the consent records, the saves and the journals are), the key inside a word the door sends the game (if you pasted it into `--model` by mistake), a `--base-url` carrying a password or a token, or the SDK's own logging switched on (`ANTHROPIC_LOG`), which writes a request's particulars on the terminal. Each refusal says why without the key. A test reads every file of the repository for the shape of a key and fails on any.

**OpenRouter.** `--dialect openrouter` speaks OpenRouter's form of the API (the local runner's chat completions) with OpenRouter's key: `--store-key --dialect openrouter` puts it in the store under the account `openrouter`, or `FREESAIL_OPENROUTER_KEY` (or `OPENROUTER_API_KEY`) in the environment. `--model` is OpenRouter's name for the model (`vendor/model`, as its list has it). The door marks nothing for a cache there and says no running total of what was used (each reply's count still goes to the game, as the runner's does), and it needs `--ctx` for the officer's station, as an Ollama model does. **Its exchanges** (package 45c): `--exchanges FILE` writes there as at the Anthropic dialect, one JSON line per request (`request`, the body sent with no header and no key; `status`; `reply`, the reply as read), appended to the file, which you name outside the game's folder; a reply the door could not read is written whole there and its shape said in the door's terminal. The free models' common shapes are read: the reply's `reasoning` (or `reasoning_content`) field beside empty content, a tool call written in the text (a `<tool_call>` tag, a fenced JSON block, or the reply a call's object alone), and empty content with the finish reason said.

**Pictures: the chart and the ship's view.** At the API door and over MCP (Claude Desktop and Claude Code read a picture in a tool's result), the model has two more tools: `chart`, the chart by the ship's account, and `ship_view`, the ship as the viewer draws her, from any side (`facing`: degrees from the bow, `90` the starboard beam, or `leeward`). With no browser open (the console) the tool says so and gives the readings the picture would have shown. **What a station sees**: the picture itself in the tool's result, with a line saying what it is ("The chart by the ship's account, the ship at the centre, the coast span, twenty miles across, at 05:50: a picture of 1200 by 900 pixels"). A picture is a book (section 5, the shelf): it costs its tokens on every turn until the model shelves it, and it is put back only by the model's own hand (package 45c: it went back by itself after three turns, and the owner's models, finding it gone, doubted they had seen it and then doubted the journal they had written with it open); once put back, its place in the conversation holds a line saying what it was, **that it was shown**, and the model's own note of it ("A picture: put back the chart at 05:50 (the coast span, twenty miles across) (book 3); seen: the Manacles on the quarter, her sails full. The picture itself is kept in the game's memory only; the transcript notes that it was shown, with its size, the span and the side asked, and nothing of it is in the journal, the log or the save. The browser's chart has the same spans as buttons beside *centre* and *fit*.

**The replay.** Everything a station does to the game is the game's input from this package on (section 12), and so is a station bound or unbound by hand (section 15): a game played with the API door, or any other, replays on a later build to the same log. The transcript is kept as the record.

## 18. The regatta: a course sailed by an agent, and scored (package 44)

The regatta (spec M6 §21) sails a fixed course at a fixed seed under one agent at a time and scores the run: the elapsed time from the gun to the finish line, with the damage, the groundings, the crew's fatigue and the purse beside it. It is your tool for judging the physics and the documentation against the models, and the first competitive mode. One command runs a course; there is no game to start first, since the regatta hosts the game itself and the door runs beside it.

**The courses** are in `data/regatta/`: `ushant-to-falmouth.yaml` (the frigate, gate 5b's passage), `falmouth-to-bertheaume.yaml` (the schooner across the Channel, the merchant passage's crossing) and `falmouth-to-funchal.yaml` (the schooner to Madeira on the whole chart, by way of Ushant and Cape Finisterre, each left to larboard). Each says which scenario gives the ship, the time and the weather, what every agent is given at the gun (plain sail), the finish (a place and a radius) and the limit, and the marks: a mark is rounded when her track crosses the line laid from it to seaward, so a ship that cuts inside it has not rounded it. The judge reads her true position, which no agent ever reads. `--ship data/ships/cutter.yaml` (or `ship:` in a course file) sails the same course in another ship, so that a new hull is tried beside the others.

**The agents**, by `--agent`:

```
py tools/regatta.py data/regatta/ushant-to-falmouth.yaml --agent rules
py tools/regatta.py data/regatta/ushant-to-falmouth.yaml --agent fake
py tools/regatta.py data/regatta/ushant-to-falmouth.yaml --agent local -- --endpoint http://127.0.0.1:8080 --seed 7
py tools/regatta.py data/regatta/ushant-to-falmouth.yaml --agent api -- --model "THE MODEL'S NAME, AS THE API NAMES IT" --effort high
py tools/regatta.py data/regatta/ushant-to-falmouth.yaml --agent replay --save saves/my-run.json
```

- `rules`: the rules-based captain on the course's intent, nobody seated.
- `fake`: the scripted captain at the captain's station (`--fake NAME` runs one of the course's other scripts, as the trims by a point of sail were judged).
- `local`: a model under `llama-server` or Ollama through the local runner (section 5). Start the model server as always; everything after `--` is the runner's own flags (`--endpoint`, `--seed`, `--model`, `--ctx`, `--max-reply`, `--cadence`, `--pictures`, ...). `--station captain` is given for you.
- `api`: a model through the API door (section 16), the key from your credential store as always; after `--` the door's flags (`--model` is required, `--effort`, `--dialect openrouter`, `--max-reply`, ...).
- `replay`: your own game of the course. `py tools/regatta.py <course> --start-save saves/gun.json` writes the course at the gun as a save; load it (`py -m freesail.ui.console --load saves/gun.json`, or the browser's server with `--load`), sail her in, and save; `--agent replay --save` your save replays it by its journal and judges it as it sails. A save that did not start from the course's gun is refused in words.

**Consent.** The regatta runs a model only with its consent on record: a yes that stands for the brief as it is, with the drill passed (the captain's station drills). Without one the door is refused before the gun in words that say why (`The regatta runs no model whose consent is not on record ...`), the runner or the door ends with exit code 5, and nothing is written; no consent question is put at the regatta. Put the question in a game first, at the captain's station (section 14), and come back. The regatta is a kind of session the consent brief names since package 42b's revision (decision 48).

**At lockstep.** The scripted agents answer within the tick. For a model's door the clock holds at the gun until the station is taken, and after that holds for every turn while the door has the floor (section 8), so a slow model loses no time to its thinking: the race is the ship's time, not the machine's. The station is sampled every glass and on the notable and urgent lines (`--cadence` after `--` changes it). When she crosses the line, or the limit is reached, the regatta stands the station down with your own `stand down the captain` and the door ends (exit code 3).

**What it writes.** Each run writes, under `docs/playtests/regatta/<date>/<course>/`, its log (the play log as the log has it) and its row (`<agent>.json`), and writes the date's table (`docs/playtests/regatta/<date>/table.md`) again from every row of the date: a course to a section, the finishers first by their time. A model is named in the table and the log by its kind and its door ("a local model through its runner", "a hosted model through the API door"), never by its name, which the regatta puts in place of the name wherever the log has it; `--label` names a run beside its kind (a second run the same day is kept as `local-2`), and `--note` adds a line under the course. The run's save goes to `saves/regatta/`, from which it replays to the digest the row gives; copy the date's folder back into the repository with the gate report as you do the consent records. `--no-write` scores a run and writes nothing; `--table <date folder>` writes a table again from its rows.

The first table, the rules-based captain and the scripted captain on the three courses at seed 7, is in `docs/playtests/regatta/2026-10-16/` (tuning notes, package 44). No model has been run on a course yet; that is yours.

**The doubt, and the `[reason: ...]`** (decision 50). The channel keeps the one rule with the model: an order the simulation could not have produced on its own from where it is (a sail put inside your lookout's horizon in clear daylight, a low deeper than the season's floor or a deep one out of a steady glass, a letter by a cutter from a port she is far from, a thing found aboard with no cause, a price moved by a third) is **doubted, not refused**: the result says why and that *if you think the action you requested is still reasonable, you may enter it again along with a `[reason: ...]`, and it will be logged and performed*; entered again so, it is done, and the director's log keeps the act, the doubt and the reason together. **The director's voice** (package 52; spec M7b §8, §9, §15; `docs/primer/20-the-director.md` has the forms). The director (a model or you at its seat) may now make people and speak for them:

- **A person from words**, who stays in the world: `person: make "Mr Fox", a Guernsey pilot of sixty, ashore at Brest, who knew the captain's father` (who he is, his age, where he is and a line of history, in any order after the name); then `person: "Mr Fox" comes aboard as master` (he comes aboard and the master's station is bound to him, so that a model seated at the master's is in his place, his outline in its brief), `person: "Mr Fox" goes ashore` (at the nearest port), `person: "Mr Fox" leaves the ship at Falmouth` (his station goes back to the ship's own master, or is unbound). Such an order is refused, in the director's log, with the stations held named; the director reads them in its truth too.
- **Questions to people nobody holds**: while a director is seated, `ask the cook what is for dinner` (from you or from a station) is put to the director in its next sample; it may answer as him with `say as` (an answer costs none of its day's acts), and the answer goes back to the station that asked, waking it; unanswered within a glass, the station is told so. With no director seated, such a question is refused in the words it always was. The masthead (an unheld lookout) and the master's reckoning still answer by the rules whoever sits above.

**The director's hand** (package 62; spec M7b §3; `docs/primer/20-the-director.md` has the forms). The director (a model or you at its seat) may give another ship's captain an order of her own grammar as his own, without seating anyone and without a second conversation: `ship "Harpy": order heave to`, `ship "Harpy": order give chase`, `ship "Harpy": order shape a course for Falmouth`. Her log says it as her captain's ("By the captain: heaving to."), never yours or the director's; the director's log keeps it as the director's act, with its doubt and reason as every act; your play log shows only what your lookout sees of her. Her captain holds by it a glass, or until the director's next order to her, then sails by his intent again; `ship "Harpy": order carry on` gives her back sooner. **The hold may be named** (package 66): `ship "Harpy": order heave to for a watch` (`for two glasses`, `for an hour`), or `... until a sail within hail` (`a sail in sight`, `a landfall`, `hove to`, `at anchor`), her own events read from where she is: she holds past the glass until the event comes to her, a day at most, and the result says until when.

- **Crewed** (within four miles of you, the cap allowing), the order goes to her own World as her captain's, under his own domain: what she cannot do is refused in her words, and the director can do nothing through her captain that her captain could not.
- **At far detail** her body is the plan's, and she carries only the far shape's orders (a course shaped or steered, heave to, fill away, give chase, haul off, make or shorten sail, an anchor, weigh, keep the station). Anything else (a sail by name, a boat lowered) is answered honestly as an order the game has no way to perform as said, and logged as attempted when entered again with a reason. Within the promotion's range the answer says the director may ask for her crewed first: `ship "Harpy": crewed` makes her a full ship now if the cap has room, and is refused in words beyond the range or with the cap full (your budget, and the cap's order, stand).
- **The doubt** bites only where the order itself is implausible for her: an anchor let go deeper than thirty fathoms, plain sail in a gale, a merchantman, a fisherman or a packet giving chase. Entered again with a `[reason: ...]`, it is done.
- **The refusal: the rule of reach.** Where a model or you hold her captain's station (a model seated as her captain through a door, `--station captain --ship <id>`, or under the director's `seat:`), the order is refused outright, in words naming who holds him, and logged: *her captain is held by a model: his orders are his holder's own, and nobody gives one through him; write to him instead*. Your own ship is never the hand's, whoever holds her captain.

You may give the same order yourself as the owner (`world: ship "Harpy": order heave to`), undoubted, the rule of reach still standing. A letter to a model captain of another ship has no form yet (`message:` reaches your own ship), so "write to him" is said and is not yet a road; the tuning notes carry it for the lead.

`ask the director`, `tell the director` and `show the director's journal` stay refused: the director's log is read by name, and your word reaches it by the brief (`director: brief ...`).

**Who commands, told to the stations below the captain's** (package 52). A model at the officer's, the master's, the lookout's or a passenger's station is told in its session kind who is over it: you, the human captain at the prompt (with the rules-based captain sailing her by his book under you on an intent scenario); a model at the captain's station; or the rules-based captain by his book, when you are seated elsewhere (`--seat director`, `--seat officer`). When that changes while it is seated, its next sample says so once.

## 20. The needs: hunger, thirst and sleep at a station (package 54)

A person at a station held (yours at the prompt or your seat, or a model's) eats, drinks and sleeps by his own hand; everyone nobody holds is the routine's, fed at the meals and asleep in his watch below, and never shown (spec M7b §19 and §20; `docs/primer/19-the-wardroom.md`, "Hunger, thirst and sleep", has the steps and the orders). Nothing here asks anything of a door: the needs come in the samples a station already reads.

**The needs in a station's sample.** Each need rises in steps with the hours since the person last ate, drank or slept (`data/crew/needs.yaml`). The first step is never said; when a need reaches a step that is said, the station's next sample carries a notice in the person's own words with what he may do ("You are quite thirsty. (submit_order('drink'))"), a notable one at the change of the watch and at most one a watch, an urgent one at once (an urgent need wakes a stand-by as an urgent line does); and while any need is at a step that is said, the sample carries it under `needs` ("quite thirsty and feeling a bit drowsy"), absent otherwise. None of it is in the log, a `read_log` or any other station's sample; the player at the prompt reads his own at the console and in the browser's log pane.

**The person's own orders.** `submit_order('eat')`, `submit_order('drink')` (`drink the foul water` when the water is found foul and there is no beer), and `submit_order('how am I')` are every station's, whatever its domain (the director's excepted: it has no body), answered to the station alone and never written in the log; a replay by the acts gives them again. `short allowance` and `whole allowance` are the captain's, with a notable line.

**The stand-by asleep below** (the master's suggestion). `stand_by('asleep below until called')` turns the station's person in below (the captain to his cot in the cabin, an officer to his cabin off the gunroom) and stands it by until it is called: a word or a question to it, an urgent line (and, for a station with the deck, a notable line that speaks of danger), or the person waking rested (eight hours of waking made up an hour below). Its log line is the stand-by's ("[officer of the watch] Turned in below, in the gunroom, asleep until called."); woken, the person goes back where he turned in from, and the sample says so first among its notices. It is refused with the deck below the captain's (hand the deck over first) and within the hour of the last sleep; `submit_order('sleep')` from a model is answered with the stand-by's words. A person who goes past fatigue's last step falls asleep where he stands: the station stands by, asleep, until called, with nothing in the log and a line in its own journal.

**Who has needs by hand.** A model's station's person; the player's seat's; and the captain while you are at the prompt (a driver listening, the console or the browser) and no model holds his station, or after an order of your own needs. A test or a passage sailed by its book has nobody at the prompt, and its captain is the routine's: so no recorded passage's log or pin moves for the needs. While a model holds the captain's station, `eat` at the prompt is refused: you are the owner there, with no needs to see to.

## 21. People in places: where a station's person is, the reach, the books, several officers (package 53)

A place is part of a person's state and of what he can do there, not a simulation of its own (spec M7b §14, §16, §17; `docs/primer/14-the-port.md` and `19-the-wardroom.md`). **Every person is somewhere**, you among them: at the prompt you are the captain, on the quarterdeck unless you went elsewhere; a model at its station, or you at your seat, is the station's person (Mr Pearce for the officer of the watch on the frigate).

**Going about the ship** is any station's, with the deck or without, whatever its domain: `go below` (the captain to his cabin, anyone else to his berth: the gunroom, or the galley for the cook), `come on deck` (or `go on deck`), `go to the gunroom` (any place aboard but the captain's cabin, which a man reaches by being sent for), `go aloft`. The people, `where is` and the muster say where each is ("Mr Pearce, off watch, in the gunroom"; "with the deck, in the gunroom"). **The deck's orders are given from the deck**: the sails, the yards and lines, the helm and the course, the anchors, all hands. From the cabin, the gunroom or ashore they are refused in words that name the way back (*You are in the gunroom; go on deck to make or take in sail.*), so a model that went below reads at once what to do. Everything else (the people, the port's business by the boat, the reckoning, the standing orders, the deck's conversation, every reading and the library) is given from anywhere. Nothing moves a person by itself but the boat and the watch's routine.

**Ashore.** At anchor in a port, `go ashore` sends the boat with you and lands you at the quay; she comes back without you. The port's places are the quay, the market, the counting house, the tavern and the pilots' office, and a port's own (Falmouth's packet office, Plymouth's dockyard): `the places ashore` lists them in port or ashore, what is done in each and who is found there, the people of the world among them by name (any station may ask it); `go to the market` takes you there. **The market is ashore in person or aboard by the boat**: at the market, `buy 10 tons of tin` is struck there and then (you read the prices yourself; the tin comes off by the port's lighter, and the log says when it is in the hold); aboard, as always, by the boat. Ashore the deck's orders and the boat are refused, and the ship's people are out of hail (`tell the mate ...` is refused: a letter by the boat reaches him); `come aboard` sends the boat for you.

**Books drafted** (spec M7b §16). `draft a book "night orders": standing order "lead": every glass then heave the lead; "dusk": at sunset then take in the royals` writes a standing-orders sheet; `draft a book "cargo": buy 20 tons of tin; sell 5 tons of salt` a manifest; anything else a note for the ship's papers. Each carries the drafter's mark and the hour and is in the library under `books` for every station (`library(topic='books', section='night orders')`), and at the prompt `the books` and `show the book "cargo"`. `post the book "night orders"` makes the sheet's orders standing orders in the poster's rank (an officer posts his own; a line in another's rank is refused); `give the book "cargo" to the boat` strikes the manifest's bargains together and sends the boat once. A model at a station may draft and read any book; posting is judged as the standing orders it gives, and the manifest as the port's business, kept back from an officer as that is.

**Several officers.** The frigate has three stations of the officer of the watch's kind: the officer of the watch's own (the first lieutenant, Mr Pearce), the `second officer` (Mr Pascoe, the starboard watch) and the `third officer` (Mr Russell, the larboard watch). A door asks for one by its name, its number or its person: `--station "officer 2"`, `--station "second officer"`, `--seat "Mr Russell"`. Each one's brief says who is first and whose watch is whose. You give the deck to whom you name (`Mr Russell, you have the deck`), and `I have the deck` takes it from whoever has it. **The deck passes by the watch bill**: when an officer who keeps a watch has it and another officer's station is held, at the change of the watch (on the hour; the dog watches at four, six and eight) the deck goes to the officer whose watch comes on deck, with your night orders, what your word allows him and the last handover note, and one line of the log says so. The first lieutenant keeps no watch: the deck given to him stays his until you take it; and an officer whose relief nobody holds keeps it.

## 21a. The station's line and the stand-by (package 66)

The dispatches test (`docs/playtests/2026-10-18-dispatches-director-test/`) found a captain who could not tell where he stood, lost three orders to his own stand-by, and was woken with nothing to read; and a director who could not read the truth while it stood by. Package 66 mends those (spec M7b §5 and §14, "as built (package 66)").

**The line.** Every sample of a seated person opens with one line of his own, before everything else in it (the sample's `you`, first in its data; the REPL and the MCP bridge print it under the sample's head): who he is, where he is and since when, whose the deck is, and his state in the needs' words when they have any:

```
You: the captain, ashore at Falmouth, at the market, since 10:38; the deck yours; on your feet since 10:00.
```

The deck is *yours*, another's by name (*the deck Mr Pearce's*), *the captain's*, *the captain's book's* (a model at the captain's station without it) or *nobody's*. The director's line says the director's: *You: the director, above the game; the day's budget 3 of 48 samples and 1 of 48 acts used; the clock waits on you and the captain* (every station whose open sample holds the clock at 1x). `how am I` answers with the same line, then the hours since the person ate, drank and slept. The line is the sample's and never the log's, so no recorded passage moves.

**The stand-by's end.** An order (`submit_order`), a world order, an answer or words of a model's own, sent while it stands by or waits for its turn (a door that keeps its own conversation, the MCP bridge or the REPL, sends them out of turn), end the stand-by at once, logged *The captain ends its stand-by (until a glass) at its own word; it is sampled again.*, open the turn and are run in it; the door's answer says so (*Your stand-by (until a glass) ended at your own order, and your turn opened with it: what you sent was run in it.*). The replay opens and runs it at the same point. The meanwhile reads stay as they were and do not end it: `read_log`, `readings`, `state`, `library`, `read_journal`, the pictures, and at the director's station `truth` and `chart`; so do a journal note and shelving a book. Nothing is dropped with *Nothing was run* any more but while a station is paused.

**A wake carries a line.** A stand-by's event (and a notable line that samples a station by its cadence) wakes a station only when the line reaches it: a word said in a place (a `say`, a station's words, a person's words, a word told or asked, an answer) when its hearers name the station or it was said within its earshot, or to it; the ship's own lines from her log, wherever the station's person is; the director everything. A word said ashore is heard at the same place of the same port.

**Who heard.** A `say`'s result names who heard it, the stations held first and then the people within hearing by name (*Heard by Mr Veale, ashore at Falmouth, at the counting house.*; *heard by nobody, in the gunroom*); the log's line is unchanged. A question put to a person nobody holds while a director is seated says in its result until when it waits (*his answer is awaited until 11:08, when the glass is out*). The director's `say as` says who heard it in the director's log.

**Merchant words.** On a ship that is no King's ship (her wardroom file binds the captain's station to a master, or with no file her rules-based captain sails by the merchant's, the packet's or the fisherman's doctrine), the officer of the watch bound to nobody is *the mate* in the station's brief and every default word, never *the first lieutenant*.

## 22. The harbour and the settings (package 59)

The terminals, the flags, the desktop client's configuration and the scenarios by hand are now one page: **the harbour**, a page of the game's own server (spec M7b §21d, §21e). In the game folder:

```
py -m freesail
```

It prints `FreeSail harbour. Open http://localhost:8000/harbour`, the settings file it read, and that the clock is held until the driver says go, and opens your browser on the harbour. Leave the terminal open (it is the game's server, and prints its lines about the models as in section 2). `py -m freesail --no-browser` opens nothing; every flag of `freesail.ui.server` is taken too (`py -m freesail --scenario data/scenarios/smack-falmouth.yaml --seat officer` starts that game at once, the harbour beside it), and a flag given wins over the settings for that run. Under *settings* the harbour offers a shortcut: on Windows `FreeSail.cmd` on your desktop, which goes to the game folder and runs `py -m freesail`.

**The headless start.** Every start, from the harbour or by hand, holds the clock at tick 0 until the driver says `go` (the game page's *go*, or `go` at its order line): a door can be seated, a brief given, the settings checked, before anything happens. `time N` (or `speed N`) is a driver command at the console and the game page's order line alike, as `hold`, `go` and `tick N` are.

**The page's four parts.**

- **game**: what is in play (the scenario, the ship, the ship's time, the seed, where you sit, the director's brief, the pace), the stations held and by whom (a model's name and door, or *the player*), and the doors started from the harbour. *A new game* takes the server's flags as controls: a scenario (the game's and your own), a ship file or a save; the seed; your seat (as the scenario says, the captain at the prompt, or the officer, master, lookout, passenger or director); the compression; the pace (the pace rule, lockstep or free-running); the crewed cap and range; the business on or off; a director's brief (a starter, a file or your words); a book of standing orders. *start the game* replaces the game in play with the new one in the same server (every open game page reloads onto it) and prints the scenario's lines; *go to the game* opens the game's page. The harbour stays at `/harbour` while a game runs; the game page's *harbour* link opens it.
- **doors**: tick the stations a door is to ask for (and the other ship, for a station aboard her). *show the entries* shows the desktop client's whole configuration file as it would read with one entry per station ticked, `freesail-captain`, `freesail-officer`, `freesail-director`, ... (below); *write them* writes it on your word, keeping the old file beside it as `.bak` and every other server in it. *start the API door* and *start the local runner* start the door for each station ticked as a process of the game's server, with the model and the flags from the settings; each has a pane with its output as its terminal would show it, a line at the foot to type into its terminal (your word to the model in the consent conversation, the same as at a terminal: a blank line ends it), and *stop*. Stopped, the door releases its station (at Windows, where there is no Ctrl-C to send it, the door is ended and the game releases the station). A door that ends of itself says so in its pane, with its exit code in words (*it could not reach the game or its model, or would not start*: its last lines say why). The credential store's state is shown: whether a key is there, never the key.
- **scenario maker**: read any scenario (the game's or yours) into the form, change what you want, *prove it* (it is loaded as the console would load it, its World made and its first orders given; a refusal is shown in the loader's own words) and *save in my scenarios*. Only the fields you touched are written again: every other line of the file, comments and all, stays as it was, so a scenario read and saved with nothing changed is the same file byte for byte. *a new scenario* starts from a blank cutter in Carrick Road. The start is a port's road, or a place you click on the chart of the region; the weather the month's climatology or the wind pinned by the hour; the other sail with their intents, the world orders by time, the books (a starter, or one you draft there, written beside the scenario), the first orders; **the stations and who holds them** (`stations:` in the file: `player` is your seat, which either driver takes as `--seat`, `model` a model's door, `rules` the game's own); and the director's brief, a starter, a file, your words, or written in the form with its limits (started from a starter if you like). Your scenarios are saved in your scenarios place (the settings), never in the game folder, and listed by the harbour as yours.
- **settings**: the file `%APPDATA%\FreeSail\settings.yaml` (on macOS `~/Library/Application Support/FreeSail/`, elsewhere `~/.config/freesail/`; `FREESAIL_SETTINGS` names another): the game's defaults (seat, compression, pace, crewed budget, port), the places (saves, your scenarios, the consent records, the desktop client's file), and for each door the model's name and its flags (the bridge's model name as the client's menu shows it; the API door's model, dialect, effort and flags; the local runner's endpoint, model and flags). **No key is ever in it**: the API door's key stays in the credential store, put there once at a terminal with `py -m freesail.agents.api --store-key` (section 16); the settings refuse a field named for a key, anything of a key's shape and the store's own key, and nothing is written. A model's name may live in the settings, and the harbour puts it only into the desktop client's file and a door's command line: nowhere in the game folder, a save or a log. (A model seated through a door is in the save and its consent record by its own identity, as it always was.) The consent records' place is read when the server starts: change it, then start the harbour again.

**The desktop client's entries.** The client starts each server in its configuration once and shares it among all its chats; so one bridge is one station, and **one entry per station** is how several chats hold several stations of one game. The entry for the director, as the harbour writes it on Windows (the model's name from the settings, or a placeholder telling you to set it there):

```json
"freesail-director": {
  "command": "py",
  "args": ["-m", "freesail.agents.mcp_server", "--game", "http://localhost:8000",
           "--station", "director", "--model-name", "THE MODEL'S NAME, FROM YOUR SETTINGS"],
  "env": {"PYTHONPATH": "<the game folder>", "PYTHONUTF8": "1"}
}
```

After writing, **quit the client completely** (the icon by the clock, *Quit*) and start it again; each entry's tools are listed under its own name in the tools menu.

### Several stations from several chats

The owner's testing regime (2026-10-18): one game, several stations, each held from a chat of its own.

1. Start the game from the harbour (the scenario, your seat, the director's brief). Tick the stations the models are to hold (say the captain and the director), *show the entries*, *write them*, and restart the desktop client.
2. Open **one chat per station**. Tell each chat which station it is and to use **that entry's tools alone**: *"You are the captain in FreeSail. Use only the freesail-captain tools; connect and read what the harness sends you."* Where the client lets you, switch the other `freesail-*` entries off for that chat in its tools menu. A chat that calls another entry's tools reaches that station's bridge.
3. **Consent is asked once per model name**, at the first station that model takes in the game's records; the record is kept under the name, and the next station the same model takes (the director after the captain) is seated by the record already given, through the game's own step as always.
4. **A second chat reaching for a station already held attaches to it**: the bridge is one process per entry, so a second chat using `freesail-captain` is the same captain, the same conversation, attached by the game as a door that comes back. Hold one station per chat; if you want a fresh conversation at a station, stand it down first.
5. The harbour's *game* part shows which stations are held and by whom while you play.
